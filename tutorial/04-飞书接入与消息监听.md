## 一、飞书机器人原理

### 1.1 本节学习目标

- 理解飞书消息流转的完整链路
- 区分 WebSocket 与 Webhook 两种接入方式
- 知道为什么 XiaoPaw 选 WebSocket

### 📖 概念小课堂：什么是"机器人"

**机器人（Bot）** 是飞书里的一个特殊账号，由程序控制而非真人操作。用户在飞书里给机器人发消息，程序通过飞书 SDK 接收并处理，再调用 API 回复用户。

打个比方：机器人就像公司前台的"自动应答机"，用户按按钮（发消息），机器根据按钮选择对应的录音回复（程序处理）。

### 1.2 消息流转机制

飞书机器人通过 WebSocket 长连接接收消息，无需公网回调地址：

```
用户在飞书发消息
       │
       ▼
飞书服务器
       │ (WebSocket 推送)
       ▼
XiaoPaw 的 FeishuListener
       │ (解析事件)
       ▼
构造 InboundMessage
       │
       ▼
Runner.dispatch() 处理
```

**流程解释**：

1. 用户在飞书 App 里发消息给机器人
2. 飞书服务器把消息推送到我们维护的 WebSocket 长连接
3. `FeishuListener` 接收事件，解析出文本内容
4. 构造 `InboundMessage` 对象，包含路由键、内容、发送者等
5. 调用 `Runner.dispatch()` 进入消息队列处理

### 1.3 为什么用 WebSocket 而不是 Webhook？

📖 **概念小课堂**：两种接入方式：

- **Webhook（回调）**：飞书主动发 HTTP 请求到你提供的公网 URL，你需要一个公网服务器
- **WebSocket（长连接）**：你的程序主动连到飞书服务器，建立长连接，飞书通过这条连接推送消息

打个比方：

- **Webhook** 像快递送货上门——快递员（飞书）必须知道你家地址（公网 IP），且家门必须开着（HTTPS 服务运行中）
- **WebSocket** 像你主动打电话给快递员，建立通话后保持连接，他通过这条电话告诉你"有新快递了"——不需要公网号码，只要你能拨出去就行

#### 对比表

| 方式 | 需要 | 优势 | 劣势 |
|------|------|------|------|
| Webhook | 公网 IP + 域名 + HTTPS 证书 | 实时性好、可水平扩展 | 部署门槛高、需备案 |
| WebSocket | 仅需出站网络 | 本地开发可用、零公网依赖 | 单连接限制、需维护重连 |

💡 **实际场景**：本地开发时，小明的笔记本没有公网 IP，用 Webhook 完全无法调试。WebSocket 只需要能访问外网即可，所以 XiaoPaw 选了 WebSocket。

## 二、飞书应用配置

### 2.1 本节学习目标

- 在飞书开放平台创建一个机器人应用
- 配置所需权限
- 启用 WebSocket 接收模式

### 2.2 创建飞书应用

1. 访问 [飞书开放平台](https://open.feishu.cn/) → 开发者后台
2. 创建企业自建应用
3. 复制 **App ID** 和 **App Secret**（这两个值是机器人身份凭证）

📖 **概念小课堂**：App ID 像你的身份证号，App Secret 像你的私钥。两者配合用于身份验证：飞书服务器验证你的程序"是不是它声称的那个机器人"。

### 2.3 配置应用能力

| 权限 | 用途 | 必需 |
|------|------|------|
| `im:message:receive_v1` | 接收消息事件 | 是 |
| `im:message:send_as_bot` | 以机器人身份发消息 | 是 |
| `im:resource` | 获取消息中的图片/文件 | 否 |
| `contact:user.base:readonly` | 获取用户基本信息 | 否 |

**权限解释**：

- `im:message:receive_v1`：开启后，机器人能"听到"用户发来的消息
- `im:message:send_as_bot`：开启后，机器人能"说话"——调用发送消息 API
- `im:resource`：如果用户发图片，机器人能下载图片内容
- `contact:user.base:readonly`：能查用户姓名（用于日志显示更友好）

### 2.4 启用 WebSocket 模式

飞书后台 → 事件与回调 → 选择"使用长连接接收事件"

📖 **概念小课堂**：飞书后台的"事件订阅"决定哪些事件会推送给你的机器人。开启 WebSocket 模式后，飞书会维持一条长连接到你程序，事件通过这条连接推送。

### 3.2 FeishuListener 核心代码

"""飞书 WebSocket 消息监听器。"""
# ↑ 模块文档字符串

import asyncio

# 消息处理回调的类型签名
OnMessageFn = Callable[[InboundMessage], Awaitable[None]]
# ↑ 类型别名：OnMessageFn 表示"接收 InboundMessage 返回 Awaitable[None] 的函数"

### 3.3 FeishuListener 类定义

```python
class FeishuListener:
    """飞书 WebSocket 长连接监听器。

    职责：
    1. 维护 WebSocket 长连接
    2. 接收消息事件
    3. 防重放（同一条消息不处理两次）
    4. 限流（防止单用户刷屏）
    5. 构造 InboundMessage 并分发给 Runner
    """

    def __init__(
        self,
        app_id: str,
        # ↑ 飞书应用 App ID（必填）
        app_secret: str,
        # ↑ 飞书应用 App Secret（必填）
        on_message: OnMessageFn,
        # ↑ 消息回调函数；通常是 Runner.dispatch
        replay_cache: ReplayCache,
        # ↑ 防重放缓存实例
        rate_limiter: RateLimiter,
        # ↑ 限流器实例
        allowed_chats: list[str] | None = None,
        # ↑ 允许的群聊 ID 白名单；None 表示不限制
    ):
        self._app_id = app_id
        self._app_secret = app_secret
        self._on_message = on_message
        # ↑ 保存消息回调（下划线前缀表示"内部使用"）
        self._replay_cache = replay_cache
        self._rate_limiter = rate_limiter
        self._allowed_chats = allowed_chats
        # ↑ 群聊白名单；None 表示不限制
        self._client: lark.Client | None = None
        # ↑ 飞书 Client 实例（start() 时创建）
        self._ws_client = None
        # ↑ WebSocket 客户端（start() 时创建）
```

**逻辑解释**：

- `__init__` 只做"赋值"，不做"连接"——遵循构造函数轻量化的原则
- 所有字段都加下划线前缀（`_app_id`），表示是内部字段，外部不应直接访问
- `self._client` 和 `self._ws_client` 初始为 None，在 `start()` 中创建

💡 **实际场景**：在 main.py 中构造 FeishuListener：

```python
listener = FeishuListener(
    app_id=cfg.feishu.app_id,
    app_secret=cfg.feishu.app_secret,
    on_message=runner.dispatch,  # 把 Runner.dispatch 作为回调
    replay_cache=replay_cache,
    rate_limiter=rate_limiter,
    allowed_chats=cfg.feishu.allowed_chats,
)
```

### 3.4 start 方法详解

**`start() → None`**（异步方法）

- **参数**：无
- **返回值**：无
- **用法**：在 main 协程中 `await listener.start()`
- **注意**：本方法会阻塞当前协程，直到 WebSocket 连接关闭

完整实现：

```python
    async def start(self):
        """启动 WebSocket 监听。"""
        # 构建飞书客户端
        self._client = (
            lark.Client.builder()
            # ↑ 创建 Client 构造器
            .app_id(self._app_id)
            # ↑ 设置 App ID
            .app_secret(self._app_secret)
            # ↑ 设置 App Secret
            .build()
            # ↑ 构建最终 Client 实例
        )

        # 注册消息事件处理器
        event_handler = (
            lark.EventDispatcherHandler.builder("", "")
            # ↑ 第一个空串是 verification token（WebSocket 模式不需要）
            # ↑ 第二个空串是 encrypt key（不加密）
            .register_p2_im_message_receive_v1(self._handle_message)
            # ↑ 注册"接收消息"事件的处理器
            # ↑ 当消息到达时，SDK 会调用 self._handle_message
            .build()
        )

        # 启动 WebSocket 客户端
        self._ws_client = lark.ws.Client(
            self._app_id,
            self._app_secret,
            event_handler=event_handler,
            # ↑ 把事件处理器传给 WebSocket 客户端
            log_level=lark.LogLevel.INFO,
            # ↑ SDK 日志级别：INFO
        )

        # 在子线程运行 WebSocket（lark SDK 是同步的）
        loop = asyncio.get_event_loop()
        # ↑ 获取当前事件循环
        await loop.run_in_executor(None, self._ws_client.start)
        # ↑ run_in_executor 把同步函数放到线程池执行
        # ↑ 第一个参数 None 表示用默认线程池
        # ↑ 第二个参数是要执行的函数（注意：不带括号，是函数对象）

        logger.info("feishu websocket listener started")
```

**逻辑解释**：

📖 **概念小课堂：为什么要用 `run_in_executor`？**

飞书 SDK（lark-oapi）是同步阻塞的——调用 `ws_client.start()` 会一直阻塞当前线程，直到连接关闭。如果直接在 asyncio 协程里调用，整个事件循环会卡住，其他协程无法执行。

`loop.run_in_executor(None, func)` 把同步函数 `func` 丢到线程池执行，主事件循环继续运行其他协程。这就是"同步 SDK 在异步框架中运行"的桥接技巧。

打个比方：你的厨房只有一口锅（事件循环），同步任务像煮饭——需要 30 分钟但不需要你盯着。把它放到电饭煲（线程池）里，你可以腾出锅去炒菜（其他协程）。

## 四、消息处理逻辑

### 4.1 本节学习目标

- 看懂消息处理的完整流程
- 理解 5 个步骤的顺序为什么这样安排
- 学会提取消息内容、做防重放、限流

### 4.2 _handle_message 方法详解

**`_handle_message(data: P2ImMessageReceiveV1) → None`**（异步方法）

- **参数 `data`**：飞书 SDK 推送的事件对象，包含消息内容、发送者信息
- **返回值**：无
- **用法**：由 SDK 自动调用，不需要手动调用
- **注意**：内部捕获所有异常，避免影响其他消息处理

完整实现：

```python
    async def _handle_message(self, data: P2ImMessageReceiveV1) -> None:
        """处理收到的消息事件。

        流程：
        1. 提取消息内容
        2. 防重放检查
        3. 限流检查
        4. 构造 InboundMessage
        5. 调用 on_message 回调
        """
        try:
            # ↑ 用 try 包裹整个流程，防止异常影响 SDK
            msg = data.event.message
            # ↑ 取消息对象（包含消息 ID、内容、发送时间等）
            sender = data.event.sender
            # ↑ 取发送者对象（包含 open_id、sender_id 等）

            # 提取消息内容
            content = self._extract_content(msg)
            # ↑ 调用内部方法提取文本
            if not content:
                # ↑ 空内容（如纯表情、图片无文本）直接忽略
                return

            # 构造路由键（决定消息去哪个队列）
            routing_key = build_routing_key(
                msg.chat_type,
                # ↑ chat_type: "p2p"（私聊）或 "group"（群聊）
                msg.chat_id,
                # ↑ chat_id: 群聊 ID
                sender.sender_id.open_id,
                # ↑ open_id: 用户唯一标识
            )

            # 群聊白名单检查
            if msg.chat_type == "group":
                # ↑ 只对群聊做白名单检查（私聊不限）
                if self._allowed_chats and msg.chat_id not in self._allowed_chats:
                    # ↑ 配置了白名单且当前群不在白名单
                    logger.info("message from unallowed chat: %s", msg.chat_id)
                    return
                    # ↑ 静默丢弃，不回复（避免干扰）

            # 防重放：同一条消息只处理一次
            msg_id = msg.message_id
            # ↑ 飞书为每条消息分配的唯一 ID
            if self._replay_cache.contains(msg_id):
                # ↑ 缓存里已有 → 说明是重发
                logger.info("replay detected, skipping: %s", msg_id)
                return
                # ↑ 直接丢弃，不重复处理
            self._replay_cache.add(msg_id)
            # ↑ 标记为已处理

            # 限流：每用户每分钟最多 N 条
            sender_id = sender.sender_id.open_id
            # ↑ 取发送者的 open_id 作为限流键
            if not self._rate_limiter.allow(sender_id):
                # ↑ 超过限制
                logger.warning("rate limit exceeded for: %s", sender_id)
                return
                # ↑ 静默丢弃（也可改为回复"请求太频繁"）

            # 构造 InboundMessage
            inbound = InboundMessage(
                routing_key=routing_key,
                # ↑ 路由键：决定进入哪个队列
                content=content,
                # ↑ 用户消息文本
                sender_id=sender_id,
                # ↑ 发送者 ID
                msg_id=msg_id,
                # ↑ 飞书消息 ID（用于回复）
                trace_id=f"s-{msg_id[-12:]}",
                # ↑ 链路追踪 ID；s- 前缀 + msg_id 后 12 位
                ts=str(msg.create_time),
                # ↑ 消息时间戳
            )

            # 分发给 Runner
            await self._on_message(inbound)
            # ↑ 调用回调函数（通常是 Runner.dispatch）
            # ↑ await 等待分发完成

        except Exception:
            # ↑ 捕获所有异常
            logger.exception("handle message error")
            # ↑ exception() 会自动记录堆栈，便于排查
```

**逻辑解释**：

5 个步骤的顺序很重要：

1. **先提取内容**：内容为空直接 return，省去后续检查
2. **后做防重放**：避免重发消息消耗限流配额
3. **再做限流**：在确认是有效消息后限流
4. **构造对象**：通过所有检查才构造（避免无效构造）
5. **分发**：最后调用回调，把消息交给 Runner

💡 **实际场景**：如果先限流再做防重放，那么飞书重发的消息也会消耗限流配额，导致正常消息被限。所以顺序是"防重放 → 限流"。

### 4.3 _extract_content 方法详解

**`_extract_content(msg) → str`**

- **参数 `msg`**：飞书消息对象
- **返回值**：消息文本内容；解析失败返回空字符串
- **用法**：内部方法，由 `_handle_message` 调用

```python
    def _extract_content(self, msg) -> str:
        """从飞书消息对象中提取文本内容。"""
        try:
            raw = json.loads(msg.content)
            # ↑ msg.content 是 JSON 字符串，解析为 dict
            # 飞书消息格式：{"text": "实际内容"}
            return raw.get("text", "").strip()
            # ↑ 取 text 字段；不存在则返回空串
            # ↑ strip() 去除首尾空白
        except (json.JSONDecodeError, AttributeError):
            # ↑ JSON 解析失败或 msg.content 不是字符串
            return ""
            # ↑ 返回空串，让上层判断丢弃
```

📖 **概念小课堂：飞书消息格式**

飞书消息的 `content` 字段是一个 JSON 字符串，不是直接的文本。例如用户发"你好"，飞书推送的 `content` 是 `'{"text":"你好"}'`。所以需要先 `json.loads` 解析，再取 `text` 字段。

不同消息类型格式不同：
- 文本消息：`{"text":"你好"}`
- 图片消息：`{"image_key":"img_xxx"}`
- @机器人消息：`{"text":"@_user_1 你好","mentions":{...}}`

## 五、路由键设计

### 5.1 本节学习目标

- 理解路由键的作用
- 区分私聊和群聊的路由策略
- 看懂路由键构造函数

### 5.2 什么是路由键？

📖 **概念小课堂**：**路由键（routing_key）** 是一条消息的"投递地址"。在 XiaoPaw 里，每个路由键对应一个独立的消息队列，同一路由键的消息会串行处理，不同路由键的消息可以并行处理。

打个比方：路由键像快递分拣站的"目的地编码"。同一个目的地的包裹放一辆车（串行投递），不同目的地的包裹可以同时发多辆车（并行投递）。

### 5.3 路由键构造函数详解

**`build_routing_key(chat_type: str, chat_id: str, sender_id: str) → str`**

- **参数 `chat_type`**：聊天类型，"p2p"（私聊）或 "group"（群聊）
- **参数 `chat_id`**：群聊 ID；私聊时为空
- **参数 `sender_id`**：发送者 open_id
- **返回值**：路由键字符串
- **用法**：

```python
key = build_routing_key("p2p", "", "ou_abc123")
# 返回 "p2p:ou_abc123"
key = build_routing_key("group", "oc_chat_xyz", "ou_abc123")
# 返回 "group:oc_chat_xyz"
```

完整实现：

```python
# xiaopaw/feishu/session_key.py
"""路由键解析与构造。"""

def build_routing_key(chat_type: str, chat_id: str, sender_id: str) -> str:
    """根据消息来源构造路由键。

    私聊：p2p:<sender_id>      → 每个用户一个队列
    群聊：group:<chat_id>       → 每个群一个队列

    这样设计的效果：
    - 同一用户的私聊消息串行处理（不会并发导致状态错乱）
    - 不同用户的消息可以并发处理
    - 群聊中所有人共享一个队列（保证群消息顺序）
    """
    if chat_type == "p2p":
        # ↑ 私聊
        return f"p2p:{sender_id}"
        # ↑ 路由键包含 sender_id，每个用户独立队列
    else:
        # ↑ 群聊或其他
        return f"group:{chat_id}"
        # ↑ 路由键包含 chat_id，每个群独立队列


def routing_type(routing_key: str) -> str:
    """从路由键提取类型（p2p 或 group）。"""
    return routing_key.split(":")[0] if ":" in routing_key else "unknown"
    # ↑ split(":") 按":"分割，取第一段
    # ↑ "p2p:ou_123" → "p2p"
    # ↑ "group:oc_xxx" → "group"
    # ↑ 没有冒号则返回 "unknown"（防御性编程）
```

**逻辑解释**：

- 私聊用 `sender_id`：保证同一用户的消息串行处理，避免状态错乱
- 群聊用 `chat_id`：群内所有人共享一个队列，保证群消息按顺序处理

# ↑ SenderProtocol 是发送器协议（接口定义）

📖 **概念小课堂：Semaphore（信号量）**

`asyncio.Semaphore(N)` 是异步版本的"令牌桶"——同时只允许 N 个协程持有令牌。第 N+1 个协程必须等令牌释放。XiaoPaw 用它限制并发发送数，避免一次性发太多消息被飞书 API 限流。

打个比方：停车场入口的"剩余车位"显示屏——剩余 5 个（Semaphore=5）就放行 5 辆车，第 6 辆得等里面有人出来。

### 6.6 _send_with_retry 方法详解

**`_send_with_retry(request) → str | None`**（异步方法）

- **参数 `request`**：飞书 API 请求对象
- **返回值**：消息 ID 或 None
- **注意**：使用指数退避重试

完整实现：

```python
    async def _send_with_retry(self, request) -> str | None:
        """带指数退避重试的发送。"""
        for attempt in range(self._max_retries):
            # ↑ 尝试 max_retries 次
            try:
                async with self._semaphore:
                    # ↑ 获取信号量（控制并发）
                    # ↑ async with 会自动在结束时释放信号量
                    response = await asyncio.to_thread(
                        self._client.im.v1.message.create, request
                    )
                    # ↑ asyncio.to_thread 把同步调用转为异步
                    # ↑ self._client.im.v1.message.create 是同步函数
                if response.success():
                    # ↑ API 调用成功
                    return response.data.message_id
                    # ↑ 返回消息 ID
                else:
                    raise Exception(f"API error: {response.msg}")
                    # ↑ API 返回错误，抛异常触发重试
            except Exception as e:
                # ↑ 捕获所有异常
                if attempt < self._max_retries - 1:
                    # ↑ 还有重试机会
                    wait = self._retry_backoff[attempt]
                    # ↑ 取本次重试的等待时间
                    logger.warning("send failed (attempt %d), retry in %.1fs: %s",
                                   attempt + 1, wait, e)
                    await asyncio.sleep(wait)
                    # ↑ 异步等待（不阻塞事件循环）
                else:
                    raise
                    # ↑ 重试用完，抛出异常
        return None
        # ↑ 理论上不会执行到这里
```

📖 **概念小课堂：指数退避（Exponential Backoff）**

指数退避是重试策略：每次重试等待时间翻倍。XiaoPaw 的默认配置 `[1.0, 2.0, 4.0]`：

- 第 1 次失败，等 1 秒重试
- 第 2 次失败，等 2 秒重试
- 第 3 次失败，等 4 秒重试

为什么不用固定等待？因为如果是网络拥塞，固定等待会让所有客户端同时重试，加剧拥塞。指数退避让重试时间分散开，给网络恢复时间。

打个比方：打电话没人接，第一次等 1 分钟再打，第二次等 2 分钟，第三次等 4 分钟——给对方足够时间处理事情。

### 6.7 CaptureSender（开发模式）

    async def send_text(self, routing_key: str, text: str) -> None:
        self._messages.setdefault(routing_key, []).append(text)

    async def send_thinking(self, routing_key: str) -> str | None:
        card_id = f"card-{len(self._cards)}"
        # ↑ 生成唯一卡片 ID
        self._cards[card_id] = "思考中..."
        return card_id

    async def update_card(self, card_id: str, text: str) -> None:
        self._cards[card_id] = text
        # ↑ 更新卡片内容

    def get_replies(self, routing_key: str) -> list[str]:

        return self._messages.get(routing_key, [])

### 7.2 防重放缓存

📖 **概念小课堂：什么是"重放攻击"？**

**重放攻击（Replay Attack）** 指攻击者截获一条合法消息，重复发送给服务器。在飞书场景下，网络抖动可能导致飞书 SDK 重发同一条消息，这不是恶意攻击，但如果不处理，会导致同一条消息被处理多次（用户收到多条相同回复）。

打个比方：你在快递柜扫码取件，扫码后门开了。如果系统不记录"已取件"，你扫一次就开一次门，可以无限取——这就是重放漏洞。

**攻击场景示例**：

```
攻击者截获 msg_id="om_abc123"
↓
重复发送 1000 次相同消息
↓
如果不防重放：机器人回复 1000 次 → LLM 成本飙升、用户体验差
如果防重放：第 2 次开始直接丢弃 → 只回复 1 次
```

#### ReplayCache 实现

```python
# xiaopaw/observability/security.py
from collections import OrderedDict
# ↑ OrderedDict 是有序字典；普通 dict Python 3.7+ 也有序
import time

class ReplayCache:
    """防重放缓存 —— 防止同一条消息被处理两次。

    原理：飞书 WebSocket 在网络抖动时可能重发消息。
    用 LRU 缓存记录已处理的 msg_id，重复消息直接丢弃。
    """

    def __init__(self, maxsize: int = 10000, ttl_sec: float = 300):
        self._cache: OrderedDict[str, float] = OrderedDict()
        # ↑ 值存的是时间戳（何时加入的）
        self._maxsize = maxsize
        # ↑ 最大条目数
        self._ttl_sec = ttl_sec
        # ↑ TTL（Time To Live）过期时间

    def contains(self, key: str) -> bool:
        """检查是否已处理过。"""
        self._evict_expired()
        # ↑ 先清理过期条目
        return key in self._cache
        # ↑ in 操作检查键是否存在

    def add(self, key: str) -> None:
        """标记为已处理。"""
        self._cache[key] = time.time()
        # ↑ 记录当前时间戳
        if len(self._cache) > self._maxsize:
            # ↑ 超过容量
            self._cache.popitem(last=False)
            # ↑ LRU 淘汰最老的
            # ↑ last=False 表示弹出最先加入的（FIFO）

    def _evict_expired(self):
        """清理过期条目。"""
        now = time.time()
        # ↑ 当前时间戳
        expired = [
            k for k, ts in self._cache.items()
            if now - ts > self._ttl_sec
            # ↑ 加入时间距今超过 TTL 则过期
        ]
        for k in expired:
            del self._cache[k]
            # ↑ 删除过期条目
```

### 7.3 限流器

📖 **概念小课堂：什么是"限流"？**

**限流（Rate Limiting）** 限制单位时间内某用户的请求数量。XiaoPaw 默认每用户每分钟最多 20 条消息，超过则拒绝。

**攻击场景示例**：

```
恶意用户写脚本，每秒发 100 条消息给机器人
↓
如果不限流：
  - LLM 调用成本爆炸（每条消息都触发 Agent）
  - 队列被一个用户的消息塞满
  - 其他用户的消息被饿死
↓
如果限流：
  - 第 21 条开始直接拒绝
  - LLM 成本可控
  - 其他用户不受影响
```

#### RateLimiter 实现

```python
class RateLimiter:
    """滑动窗口限流器 —— 防止单用户刷屏。

    原理：每用户在 60 秒窗口内最多 N 条消息。
    超过限制的请求直接拒绝。
    """

    def __init__(self, per_user_per_minute: int = 20):
        self._limit = per_user_per_minute
        # ↑ 每分钟最大请求数
        self._windows: dict[str, list[float]] = {}
        # ↑ user_id → [时间戳列表]

    def allow(self, user_id: str) -> bool:
        """检查是否允许请求。"""
        now = time.time()
        # ↑ 当前时间戳
        window = self._windows.setdefault(user_id, [])
        # ↑ 取该用户的时间戳列表；不存在则创建空列表

        # 清理 60 秒前的记录
        window[:] = [ts for ts in window if now - ts < 60]
        # ↑ 列表推导式：保留 60 秒内的记录
        # ↑ window[:] = ... 原地修改列表（保留引用）

        if len(window) >= self._limit:
            return False
            # ↑ 当前窗口内请求数已达上限

        window.append(now)
        # ↑ 记录本次请求时间
        return True
        # ↑ 允许通过
```

#### 滑动窗口算法步骤图

```
时间轴（每分钟最多 3 条）：

第 0 秒：用户发第 1 条
  window = [0.0]
  len(window) = 1 < 3 → 允许
  window = [0.0]   ← 记录时间

第 10 秒：用户发第 2 条
  清理 60 秒前 → 都没过期
  window = [0.0, 10.0]
  len(window) = 2 < 3 → 允许

第 20 秒：用户发第 3 条
  window = [0.0, 10.0, 20.0]
  len(window) = 3 >= 3 → 拒绝！
  ❌ 不记录时间，直接返回 False

第 65 秒：用户发第 4 条
  清理 60 秒前 → 0.0 过期了
  window = [10.0, 20.0]   ← 0.0 被清理
  len(window) = 2 < 3 → 允许
  window = [10.0, 20.0, 65.0]

→ 这就是"滑动窗口"：窗口随时间向前滑动，
  老的记录自动失效，不影响新的请求
```

### 8.2 为什么需要 TestAPI？

📖 **概念小课堂：TestAPI 是什么？**

`TestAPI` 是一个 HTTP 接口，模拟飞书消息流。开发模式下不需要真实飞书连接，通过 HTTP 即可触发完整流程。

打个比方：飞机驾驶员训练时不会直接开真飞机（成本高、风险大），而是用模拟器。TestAPI 就是 XiaoPaw 的"模拟器"——让你不依赖飞书也能测试完整流程。

### 8.3 TestAPI 实现

```python
# xiaopaw/api/test_server.py
"""TestAPI —— 开发模式的 HTTP 测试接口。

功能：
1. POST /api/test/message   → 发送测试消息
2. GET  /api/test/replies    → 查看 Agent 回复
3. GET  /api/test/sessions   → 查看会话列表
"""

from aiohttp import web
# ↑ aiohttp 是异步 HTTP 框架
import json

def create_test_app(runner, sender, session_mgr, token: str):
    """创建 TestAPI 应用。

    参数:
        runner: Runner 实例
        sender: 发送器（通常是 CaptureSender）
        session_mgr: 会话管理器
        token: 认证 Token（防止未授权访问）
    返回:
        aiohttp.web.Application 实例
    """

    app = web.Application()
    # ↑ 创建 aiohttp 应用

    # 认证中间件
    @web.middleware
    async def auth_middleware(request, handler):
        """认证中间件：检查 Authorization 头。"""
        auth = request.headers.get("Authorization", "")
        # ↑ 取 Authorization 头
        if not auth.startswith("Bearer "):
            # ↑ 必须以 "Bearer " 开头
            return web.json_response({"error": "missing token"}, status=401)
            # ↑ 401 未授权
        if auth[7:] != token:
            # ↑ auth[7:] 去掉 "Bearer " 前缀，取实际 token
            return web.json_response({"error": "invalid token"}, status=403)
            # ↑ 403 禁止访问
        return await handler(request)
        # ↑ 通过认证，调用下一个处理器

    app.middlewares.append(auth_middleware)
    # ↑ 注册中间件

    # 发送测试消息
    async def send_message(request):
        """POST /api/test/message 发送测试消息。"""
        body = await request.json()
        # ↑ 解析请求体 JSON
        inbound = InboundMessage(
            routing_key=body.get("routing_key", "p2p:ou_test"),
            # ↑ 默认路由键
            content=body.get("text", ""),
            # ↑ 消息内容
            sender_id="ou_test",
            # ↑ 测试用户 ID
            msg_id=f"test_{int(time.time()*1000)}",
            # ↑ 用时间戳生成唯一 ID
            trace_id=f"s-test-{int(time.time()*1000)}",
            ts=str(int(time.time())),
        )
        await runner.dispatch(inbound)
        # ↑ 调用 Runner.dispatch 入队
        return web.json_response({"status": "queued"})
        # ↑ 返回"已入队"

    # 查看回复
    async def get_replies(request):
        """GET /api/test/replies 查看 Agent 回复。"""
        routing_key = request.query.get("routing_key", "p2p:ou_test")
        # ↑ 从查询参数取 routing_key
        if isinstance(sender, CaptureSender):
            # ↑ 只有 CaptureSender 才能查询
            replies = sender.get_replies(routing_key)
        else:
            replies = []
            # ↑ FeishuSender 不支持查询
        return web.json_response({"replies": replies})

    app.router.add_post("/api/test/message", send_message)
    # ↑ 注册 POST 路由
    app.router.add_get("/api/test/replies", get_replies)
    # ↑ 注册 GET 路由

    return app
```

## 九、设计优势与局限性

### 优势

1. **零公网依赖**：WebSocket 出站连接，本地开发可用
2. **关注点分离**：监听/发送/安全各自独立
3. **开发友好**：TestAPI 模式不依赖飞书
4. **防护完善**：防重放 + 限流双保险

### 局限性

1. **SDK 同步阻塞**：lark-oapi 是同步库，需要 `run_in_executor` 桥接
2. **消息格式限制**：飞书消息格式有特殊编码，需额外解析
3. **卡片更新延迟**：update_card 有 200-500ms 延迟

## ❓ 常见问题

### Q1：启动时报 `lark_oapi` 找不到？

**A**：飞书 SDK 未安装。运行：

```bash
pip install lark-oapi
```

或在 `pyproject.toml` 添加依赖后 `pip install -e .`。

### Q2：WebSocket 连接不上飞书？

**A**：检查三步：
1. App ID 和 App Secret 是否正确（去飞书后台复制）
2. 是否在飞书后台启用了"长连接接收事件"
3. 是否添加了 `im:message:receive_v1` 权限并发布版本

错误日志样例：

```
WebSocket connection failed: 401 Unauthorized
```

→ 凭证错误，重新复制 App Secret。

### Q3：发了消息但机器人没反应？

**A**：依次排查：
1. 看日志是否有 `feishu websocket listener started`，没有则监听没起来
2. 看日志是否有 `handle message error`，有则查异常堆栈
3. 看 `_extract_content` 是否返回空（可能是图片消息，被过滤）
4. 看是否被防重放或限流拦截（日志会有 `replay detected` 或 `rate limit exceeded`）

### Q4：群聊里机器人不回复？

**A**：检查 `allowed_chats` 配置。如果配置了白名单，群 ID 不在白名单内会被静默丢弃。日志会有 `message from unallowed chat`。把群 ID 加入白名单或留空（不限制）。

### Q5：update_card 报 "message not found"？

**A**：`card_msg_id` 不正确，或者卡片消息已被删除。常见原因：
- `send_thinking` 返回 None（发送失败），后续 update_card 用了 None
- 卡片发送时间太久，飞书已删除

解决：检查 `send_thinking` 返回值，None 时跳过 update_card。

### Q6：CaptureSender 的回复在 TestAPI 查不到？

**A**：检查 `routing_key` 是否一致。TestAPI 发消息时用的 `routing_key`，查回复时也必须用同一个。例如都设为 `p2p:ou_test`。

### Q7：限流器拒绝太快，正常用户也被限？

**A**：调大 `per_user_per_minute` 配置。默认 20，对正常用户足够；如果是企业场景多人共用一个 open_id，需要调大。

### Q8：防重放缓存导致测试时消息被丢弃？

**A**：测试时如果用相同的 `msg_id`，第二次会被防重放丢弃。解决：每次测试用不同的 `msg_id`，或者开发模式下关闭 `enable_webhook_replay_cache` flag。

### 技巧 4：常见错误信息对照

| 错误信息 | 原因 | 解决方案 |
|---------|------|---------|
| `lark_oapi not found` | SDK 未安装 | `pip install lark-oapi` |
| `WebSocket connection failed: 401` | 凭证错误 | 重新复制 App ID/Secret |
| `permission denied` | 权限不足 | 飞书后台添加权限并发布版本 |
| `replay detected` | 同一消息被重发 | 正常现象，已自动丢弃 |
| `rate limit exceeded` | 用户超限 | 调大 `per_user_per_minute` |
| `message from unallowed chat` | 群不在白名单 | 加群 ID 到 `allowed_chats` |

### 技巧 5：用日志追踪单条消息

开启 `enable_trace_id: true`，每条消息会有 `trace_id`（如 `s-om_abc123`）。在日志里搜索这个 ID，能看到完整流转链路：

```
[INFO] received message, trace_id=s-om_abc123
[INFO] routing_key=p2p:ou_test, dispatching
[INFO] worker started: p2p:ou_test
[INFO] agent executing, trace_id=s-om_abc123
[INFO] reply sent, trace_id=s-om_abc123
```

### 技巧 6：检查飞书应用配置

在飞书后台 → 事件与回调，确认：

- 事件订阅已开启
- 添加了 `im.message.receive_v1` 事件
- 选择"使用长连接接收事件"
- 应用版本已发布（草稿不会生效）
