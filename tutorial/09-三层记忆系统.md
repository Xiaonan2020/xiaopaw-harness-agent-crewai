# 09 - 三层记忆系统

> 本篇带你理解 XiaoPaw 如何让 AI "记住" 用户。读完之后，你会知道为什么需要三层记忆、每一层做什么事、以及踩坑时怎么排查。

---

## 一、为什么 Agent 需要记忆？

### 1.1 本节学习目标

读完本章你应该能回答：
- 为什么 LLM "天生没记忆"？这跟它的训练方式有什么关系？
- XiaoPaw 的三层记忆分别管什么？为什么不能合并成一层？
- 同样是"记住用户偏好"，File Memory 和 Vector Memory 有什么本质区别？

### 1.2 没有记忆的问题

LLM 本质上是一个"无状态函数"：每次调用都从零开始，它不会自动记得上一轮你说过什么。下面是一个典型的"失忆"场景：

```
用户：我是做 Python 开发的
Agent：好的，了解了。

（新一轮对话）
用户：帮我写个脚本
Agent：好的，请问用什么语言？     ← 忘了用户是 Python 开发者！
```

为什么会这样？因为每次调用 LLM，它只能看到你这一次传进去的 prompt。如果你不主动把"用户是 Python 开发者"这件事再写进 prompt，LLM 根本不知道。

### 1.3 三层记忆设计

XiaoPaw 借鉴了人类大脑的记忆机制，设计了三层记忆，每层职责不同：

```
┌─────────────────────────────────────────────────────┐
│  第一层：Bootstrap Memory（引导记忆）                │
│  ─────────────────────────────────────             │
│  时机：每次 LLM 调用前自动注入                        │
│  内容：soul.md + user.md + agent.md + memory.md     │
│  特点：始终存在，定义 Agent 人格                      │
│  类比：人的"性格"和"价值观"                           │
├─────────────────────────────────────────────────────┤
│  第二层：File Memory（文件记忆）                     │
│  ─────────────────────────────────────             │
│  时机：用户显式要求"记住某事"时保存                    │
│  内容：workspace 下的 markdown 文件                  │
│  特点：LLM 通过 memory-save 技能显式调用               │
│  类比：人的"笔记本"                                  │
├─────────────────────────────────────────────────────┤
│  第三层：Vector Memory（向量记忆）                    │
│  ─────────────────────────────────────             │
│  时机：用户问问题时按相似度检索                       │
│  内容：PostgreSQL + pgvector 向量索引                │
│  特点：语义搜索，找"最相关"的历史对话                  │
│  类比：人的"联想回忆"                                │
└─────────────────────────────────────────────────────┘
```

### 1.4 三层记忆对比表

| 维度 | Bootstrap Memory | File Memory | Vector Memory |
|------|------------------|-------------|---------------|
| **触发时机** | 每次 LLM 调用前自动注入 | 用户说"记住 X"时 | 用户提问时按需检索 |
| **存储内容** | 人格/用户画像/规则/长期记忆 | workspace 的 .md 文件 | 向量化对话片段 |
| **写入方式** | 启动时读文件 | memory-save 技能显式写 | 每轮对话后异步索引 |
| **读取方式** | 拼进 backstory prompt | 下次 Bootstrap 自动读 | 向量相似度搜索 |
| **是否可丢失** | 不可（人格没了 Agent 就崩） | 重要（用户偏好） | 可丢（只是召回变差） |
| **典型场景** | "你是谁" | "记住我是前端" | "上次说的装饰器" |
| **类比** | 性格/价值观 | 笔记本 | 联想回忆 |
| **存储位置** | 内存中拼成字符串 | data/workspace/*.md | PostgreSQL + pgvector |

### 1.5 为什么不能合并成一层？

你可能会想：直接把所有记忆塞进一个文件不就好了吗？不行，原因有三个：

1. **token 限制**：LLM 的上下文窗口有限（32000 token），如果把所有历史对话塞进去，几轮后就爆了。所以必须分层——"始终在的"用 Bootstrap，"相关的"用 Vector 召回。

2. **写入时机不同**：Bootstrap 是只读的（Agent 启动时读一次）；File Memory 是 Agent 主动写的；Vector Memory 是后台异步索引的。三种写入时机混在一起会非常难管理。

3. **故障隔离**：如果向量数据库挂了，Bootstrap 还能工作（Agent 还有人格）；如果 File Memory 权限错了，Vector Memory 还能工作。分层让故障不连锁。

## 二、第一层：Bootstrap Memory

### 2.1 本节学习目标

- 记住"四件套"分别是哪四个文件、各放什么内容
- 看懂 `build_bootstrap_prompt` 的逐行代码
- 理解为什么用 XML 标签包裹每段内容
- 知道 memory.md 超长时怎么截断、为什么要截断

### 2.2 记忆四件套

```
workspace-init/
├── soul.md       # Agent 灵魂（人格定义）
├── user.md       # 用户画像
├── agent.md      # Agent 行为准则
└── memory.md     # 长期记忆（交互中积累）
```

### 2.3 各文件内容示例

**soul.md — Agent 人格：**

```markdown
你是小趴，一个友善、专业的工作助手。

性格特点：
- 热情但不啰嗦，先给结论再解释
- 遇到不确定的问题会明确说明
- 不会编造事实

能力范围：
- 可以搜索信息（百度搜索）
- 可以处理文档（PDF/Word/Excel）
- 可以操作飞书（发消息/写文档/建日历）
```

**user.md — 用户画像：**

```markdown
用户信息：
- 编程水平：Python 初学者
- 学习目标：从零实现企业级智能体项目
- 偏好：详细解释 + 代码示例
- 时区：东八区（UTC+8）
```

**agent.md — 行为准则：**

```markdown
行为规则：
1. 回答前先理解用户意图
2. 复杂任务拆解为步骤
3. 代码示例必须可运行
4. 涉及安全操作时需确认
5. 使用中文回复
```

**memory.md — 长期记忆：**

```markdown
## 2024-01-15
- 用户正在学习 CrewAI 框架
- 用户对 asyncio 不太熟悉，需要额外解释

## 2024-01-16
- 用户完成了环境搭建
- 用户在 Docker 权限上踩了坑
```

### 2.4 Bootstrap 注入实现

下面这段代码是 Bootstrap 注入的核心。每一行都加了详细注释，建议你逐行读：

```python
# xiaopaw/memory/bootstrap.py
"""从 workspace 文件构建 Agent backstory。"""

from __future__ import annotations   # 启用"延迟类型注解"，让 list[str] 这种写法在 Python 3.9 也能用

import logging                      # 标准日志库，输出到 stderr 供运维查看
from pathlib import Path            # Path 比 str 拼路径更安全，自动处理斜杠方向

from xiaopaw.memory.config import MEMORY_HARD_LIMIT   # memory.md 的最大行数（默认 250）

logger = logging.getLogger(__name__)   # 以模块名建 logger，日志里能看出是哪个文件输出的

# 四个记忆文件的配置：tag 是 XML 标签名，filename 是磁盘上的文件名
# 这个顺序很重要——soul 必须在最前面（定义人格），memory 在最后（积累的事实）
_SECTIONS = [
    ("soul", "soul.md"),       # 灵魂文件：Agent 是谁、性格如何
    ("user", "user.md"),       # 用户画像：用户是谁、偏好什么
    ("agent", "agent.md"),     # 行为准则：Agent 该怎么做事
    ("memory", "memory.md"),   # 长期记忆：交互中累积的事实
]


def build_bootstrap_prompt(workspace_dir: Path) -> str:
    """从 workspace 文件构建 Bootstrap prompt。

    这个函数在每次创建 MainCrew 时被调用，
    把四个记忆文件的内容拼成 Agent 的 backstory。

    流程：
    1. 依次读取四个文件
    2. memory.md 超过 250 行则截断
    3. 用 XML 标签包裹每段内容
    4. 拼接成完整 prompt
    """
    # parts 是一个 list，用来收集每段拼好的字符串
    # 为什么用 list 而不是直接字符串拼接？因为 list.append 比 += 高效（O(1) vs O(n)）
    parts: list[str] = []

    # 遍历四个文件，按 _SECTIONS 顺序处理
    for tag, filename in _SECTIONS:
        # 拼出完整路径，比如 workspace_dir / "soul.md"
        filepath = workspace_dir / filename

        # 文件不存在就跳过——比如新用户还没 user.md，不能崩
        if not filepath.exists():
            continue  # continue 表示跳过本次循环，进入下一次

        # 读文件内容，统一 UTF-8 编码（Windows 默认 GBK 会乱码）
        # strip() 去掉首尾空白，避免空行污染 prompt
        content = filepath.read_text(encoding="utf-8").strip()

        # 特殊处理 memory.md：它是用户长期积累的，可能非常长
        # 如果不截断，会撑爆 LLM 的 context window（其他内容就放不下了）
        if tag == "memory":
            # 按换行切分成行列表，便于数行数
            lines = content.split("\n")

            # 超过硬上限（默认 250 行）就只取前 250 行
            if len(lines) > MEMORY_HARD_LIMIT:
                # 重新拼回字符串，只保留前 MEMORY_HARD_LIMIT 行
                content = "\n".join(lines[:MEMORY_HARD_LIMIT])

                # 打个 warning 让运维知道发生了截断
                # %d 是占位符，运行时替换成具体数字
                logger.warning(
                    "memory.md truncated to %d lines (had %d)",
                    MEMORY_HARD_LIMIT, len(lines),
                )

        # 用 XML 标签包裹内容，比如 <soul>你是小趴...</soul>
        # 为什么用 XML 标签？因为 LLM 训练数据里大量包含 XML，
        # 它能很自然地区分 <soul> 和 <user> 是不同语义的段落
        parts.append(f"<{tag}>\n{content}\n</{tag}>")

    # 最后用两个换行把所有段落拼起来
    # 两个换行（而不是一个）是为了让段落之间有视觉间隔，LLM 更容易区分
    return "\n\n".join(parts)
```

#### 代码逻辑分段解释

**第一段：常量准备**
- `_SECTIONS` 定义了文件读取顺序。这个顺序是经过设计的：先灵魂（你是谁）→ 用户画像（用户是谁）→ 行为准则（怎么做事）→ 长期记忆（之前发生了什么）。这种"由抽象到具体"的顺序符合 LLM 阅读习惯。

**第二段：循环读取文件**
- 用 `filepath.exists()` 判断文件是否存在，不存在就 `continue` 跳过。这是防御性编程——新部署的 workspace 可能只有 soul.md，没有 user.md，不能因为缺一个文件就崩。

**第三段：memory.md 截断**
- 只有 memory.md 会被截断，因为它是用户长期积累的，可能无限增长。其他三个文件（soul/user/agent）是设计期就定好的，长度可控。
- 截断策略是"保留前 N 行"——这意味着较新的记忆可能被丢掉。这是个权衡：完整保留会导致 context 爆炸，所以只能截断。

**第四段：XML 标签包裹**
- `<soul>` `<user>` 这种标签不是给机器看的，是给 LLM 看的。LLM 训练语料里有大量 XML（比如 HTML、文档结构），它能很自然地理解"标签之间的内容属于同一类"。

**第五段：拼接返回**
- 用 `"\n\n".join(parts)` 而不是 `+=`。前者一次性生成最终字符串，后者每次拼接都创建新字符串，性能差很多。

### 2.5 函数详解：build_bootstrap_prompt

| 项目 | 说明 |
|------|------|
| **参数** | `workspace_dir: Path` — workspace 目录的路径对象 |
| **返回值** | `str` — 拼好的完整 backstory prompt |
| **副作用** | 无（只读文件，不修改） |
| **抛出异常** | 文件权限错误时会抛 `PermissionError`，但通常会先被 `filepath.exists()` 拦下 |
| **调用时机** | 每次 `MainCrew` 初始化时调用一次 |

**使用示例：**

```python
from pathlib import Path
from xiaopaw.memory.bootstrap import build_bootstrap_prompt

workspace = Path("data/workspace")
backstory = build_bootstrap_prompt(workspace)
# 现在把 backstory 传给 Agent 的 backstory 参数
agent = Agent(backstory=backstory, ...)
```

**注意事项：**
1. 不要在每次 LLM 调用时都重新调用这个函数——它读 4 个文件，频繁调用会拖慢响应。在 MainCrew 初始化时调用一次就够了。
2. 如果 memory.md 经常被截断，说明你需要更积极地用 memory-save 把过期记忆归档。
3. 不要在 soul.md 里写太多内容，因为它每次都会进 prompt，长一点就多花一次 token。

### 2.6 在 MainCrew 中使用

```python
# xiaopaw/agents/main_crew.py 中的 orchestrator 方法
@agent
def orchestrator(self) -> Agent:
    agents_cfg = yaml.safe_load(...)
    cfg = agents_cfg["orchestrator"]

    # ★ 注入 Bootstrap 记忆
    # 把四个文件拼成的字符串塞进 backstory 字段
    # 这样新建的 Agent 就"知道"自己是谁、用户是谁、该怎么做事
    cfg["backstory"] = build_bootstrap_prompt(self._workspace_dir)

    return Agent(**cfg, tools=[skill_tool], llm=AliyunLLM(...))
```

### 2.7 实际应用示例：Bootstrap 如何让 Agent "知道"用户

```
用户：你是谁？
   ↓
runner 接收消息，准备调 LLM
   ↓
MainCrew 初始化：
  build_bootstrap_prompt(workspace)
    → 读 soul.md：<soul>你是小趴，友善的工作助手...</soul>
    → 读 user.md：<user>用户是 Python 初学者...</user>
    → 读 agent.md：<agent>使用中文回复...</agent>
    → 读 memory.md：<memory>用户在学 CrewAI...</memory>
    → 拼成完整 backstory
   ↓
LLM 调用：system + backstory + "你是谁？" → 推理
   ↓
Agent：我是小趴，一个工作助手，专门帮你处理 Python 相关的任务！
   （注意：它知道用户是 Python 方向，因为 user.md 说了）
```

## 三、第二层：File Memory

### 3.1 本节学习目标

- 看懂 memory-save 技能的工作流程
- 理解"显式记忆"和"隐式记忆"的区别
- 知道 File Memory 最常见的坑（权限问题）怎么排查

### 3.2 memory-save 技能

用户说"记住我是做前端的"，Agent 调用 memory-save 技能保存：

```python
# 用户：记住，我是做前端开发的
# Agent 调用：skill_loader(skill_name="memory-save", task_context="用户是前端开发者")

# memory-save 技能在沙箱里执行：
# 1. 读取 /workspace/user.md
# 2. 追加新内容（"用户是前端开发者"）
# 3. 写回文件
```

### 3.3 文件记忆的特点

```
工作流程：
用户说"记住 XXX"
  → Agent 判断需要保存
    → Agent 调用 memory-save 技能
      → Sub-Crew 在 Docker 沙箱里执行
        → 读 /workspace/user.md
        → 追加新内容
        → 写回 /workspace/user.md
  → 下次会话 Bootstrap 读取更新后的 user.md
  → Agent "记住"了用户信息
```

#### 为什么是"显式调用"？

注意：Agent **不是**自动把每条用户消息都存到 user.md，那样会让文件变得又长又乱。只有当 Agent 主动判断"这条信息值得长期记住"时，才会调用 memory-save。这种"显式调用"的好处：

1. **可控**：用户能预测什么会被记住（"记住 X" 才会触发）。
2. **精炼**：只有重要信息进 user.md，不会塞满闲聊。
3. **可追溯**：每次 memory-save 都会进 Langfuse trace，能审计。

### 3.4 权限问题（最常见的坑）

这是初学者最容易踩的坑。沙箱以 gem 用户（UID 1000）运行，需要能写 `/workspace/*.md` 文件。如果权限不对，会出现一种"诡异"现象：Agent 说"已记住"，但实际没写进去。

**完整排查步骤：**

```bash
# 第 1 步：检查文件权限
# 应该看到 -rw-rw-rw- (666) 或至少 -rw-r--r-- (644) 沙箱用户能读
ls -la data/workspace/*.md

# 如果看到 -rw-r--r-- (644)，沙箱内的 gem 用户（非 owner）只能读不能写
# 修复：
chmod 666 data/workspace/*.md

# 第 2 步：检查目录权限（目录本身也要可写）
ls -ld data/workspace
# 应该是 drwxrwxrwx (777) 或至少 drwxr-xr-x (755) 沙箱用户能进入

# 第 3 步：检查所有者
ls -ln data/workspace
# 如果 owner 是 root 而沙箱用户是 gem，需要 chown
chown -R 1000:1000 data/workspace

# 第 4 步：验证沙箱内能写
docker exec xiaopaw-sandbox bash -c "echo test > /workspace/test.md && cat /workspace/test.md"
# 如果输出 test 就说明权限正常

# 第 5 步：观察 Langfuse trace
# 看 memory-save 那一步的输出有没有 PermissionError
```

**权限不对的症状：**
1. memory-save 说"已记住"但实际没写入（沙箱报错被吞了）
2. LLM 发现 Permission denied 后"创意"绕道（写到子目录，导致 Bootstrap 读不到）
3. 下次会话召回失败
4. trace 里看到 `OSError: [Errno 13] Permission denied`

### 3.5 实际应用示例：File Memory 的完整流程

```
[Round 1]
用户：记住，我是做前端开发的，主要用 React
   ↓
Agent 判断：这是用户的长期偏好，需要保存
   ↓
Agent 调用 skill_loader(skill_name="memory-save",
                        task_context="用户是前端开发者，主要用 React")
   ↓
memory-save 在沙箱里：
  - 读 /workspace/user.md（原本是"Python 初学者"）
  - 追加："用户也是前端开发者，主要用 React"
  - 写回 /workspace/user.md
   ↓
Agent：好的，已记住你是前端开发者，主要用 React！

[Round 2（新会话，Bootstrap 重新读文件）]
用户：帮我写个组件
   ↓
build_bootstrap_prompt 读 user.md → 看到"前端开发者，主要用 React"
   ↓
Agent：好的，我用 React 函数组件的写法给你写...
   （它知道用户偏好 React，不用再问）
```

## 四、第三层：Vector Memory

### 4.1 本节学习目标

- 理解向量搜索和关键词搜索的本质区别
- 看懂 pgvector 表结构和 ivfflat 索引
- 知道为什么索引是"发射后不管"的异步操作

### 4.2 向量搜索原理（通俗版）

**关键词匹配 vs 语义匹配**

假设数据库里有这样一段历史对话：
```
2024-01-10 聊过：
用户：@ 装饰器怎么用？
Agent：@ 是 Python 的语法糖，可以用来修饰函数...
```

现在用户问："之前聊过的 Python 装饰器是什么？"

```
传统搜索（关键词匹配）：
  搜索关键词 "Python 装饰器"
  在数据库里找包含 "Python" 和 "装饰器" 的记录
  → 找不到！因为历史里写的是 "@ 语法糖"，没有"装饰器"这三个字

向量搜索（语义匹配）：
  把问题转成向量 [0.1, 0.3, 0.8, ...]（一串数字）
  把历史对话也转成向量 [0.12, 0.28, 0.79, ...]
  计算两个向量的"相似度"（余弦距离）
  → 发现两个向量很接近（语义相近）
  → 返回这段历史对话
```

**通俗类比**：关键词搜索像是"严格按字面找"——你说"装饰器"它就只找"装饰器"三个字；向量搜索像是"按意思找"——你说"装饰器"，它能联想到"@ 语法糖"，因为它们意思相近。

**向量是怎么来的？**

用 embedding 模型把文本转成一串数字（向量）。语义相近的文本，向量也相近。XiaoPaw 用的是阿里 DashScope 的 `text-embedding-v3`，输出 1536 维向量。

### 4.3 pgvector 表结构

```sql
-- schema.sql
CREATE TABLE IF NOT EXISTS memory_vectors (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- 主键，自动生成
    session_id  VARCHAR(64) NOT NULL,          -- 会话 ID（用于过滤）
    routing_key VARCHAR(128) NOT NULL,         -- 路由键（p2p:ou_xxx 或 group:chat_xxx）
    user_message TEXT,                         -- 用户消息原文
    assistant_reply TEXT,                     -- Agent 回复原文
    turn_ts    BIGINT,                         -- 这一轮的时间戳
    embedding   vector(1536),                  -- 向量（1536 维，对应 embedding 模型）
    created_at  TIMESTAMPTZ DEFAULT NOW()      -- 记录创建时间
);

-- 向量索引（加速相似度搜索）
CREATE INDEX IF NOT EXISTS memory_vectors_embedding_idx
    ON memory_vectors USING ivfflat (embedding vector_cosine_ops);
```

#### ivfflat 索引通俗解释

如果没有索引，向量搜索要扫描全表（O(n)），表里有 100 万条就要算 100 万次相似度，太慢。

`ivfflat` 是 pgvector 提供的一种近似最近邻（ANN）索引：
- **ivf**（Inverted File）：把所有向量按相似度聚成若干"簇"，每个簇有一个中心点。查询时先找最近的几个簇，再在簇内细搜。
- **flat**：簇内是"扁平"的精确搜索。

**类比**：找一本图书馆里某主题的书。无索引 = 一本一本翻；有索引 = 先按类别分区（计算机类、文学类...），找到"计算机类"分区后再在该区内一本本翻。这是用少量精度换大量速度的典型做法。

> 小白提示：ivfflat 是"近似"搜索，可能漏掉最匹配的（但概率很低）。对于"召回历史对话"这种场景，足够了。

### 4.4 向量索引实现

```python
# xiaopaw/memory/indexer.py
"""向量索引器 —— 把对话转成向量存入 pgvector。"""

import asyncio                     # 异步 IO 库
import logging                     # 日志
from typing import Optional        # 类型注解：Optional[X] = X | None

logger = logging.getLogger(__name__)


async def async_index_turn(
    session_id: str,           # 会话 ID（用于过滤）
    routing_key: str,           # 路由键（p2p/group）
    user_message: str,          # 用户消息
    assistant_reply: str,       # Agent 回复
    turn_ts: int,              # 这一轮的时间戳
    db_dsn: str,               # PostgreSQL 连接串
) -> None:
    """异步索引一轮对话。

    流程：
    1. 把 user_message + assistant_reply 拼接
    2. 调用 embedding API 转成向量
    3. 存入 pgvector

    这个函数是"发射后不管"的，不阻塞主流程。
    """
    # 没配置数据库就直接返回，不报错（保证没数据库也能跑）
    if not db_dsn:
        return  # 早退：节省一次 API 调用

    try:
        # 拼接要索引的文本：用户 + 助手 = 一段完整对话
        # 这样向量同时反映问题和回答的语义
        text = f"用户：{user_message}\n助手：{assistant_reply}"

        # 调用 embedding API，把文本转成 1536 维向量
        embedding = await _get_embedding(text)

        # 存入数据库
        await _store_vector(
            db_dsn=db_dsn,
            session_id=session_id,
            routing_key=routing_key,
            user_message=user_message,
            assistant_reply=assistant_reply,
            turn_ts=turn_ts,
            embedding=embedding,
        )
    except Exception as e:
        # ★ 关键：异常只记日志，不向上抛
        # 因为这是"发射后不管"——索引失败不能影响用户收到的回复
        logger.warning("index turn failed: %s", e)


async def _get_embedding(text: str) -> list[float]:
    """调用 DashScope embedding API。"""
    import os
    from openai import AsyncOpenAI   # 用 OpenAI SDK 兼容协议调 DashScope

    # 创建异步客户端
    # DashScope 提供 OpenAI 兼容接口，所以能用 openai 库调
    client = AsyncOpenAI(
        api_key=os.environ.get("QWEN_API_KEY"),
        base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
    )

    # 调用 embedding API
    response = await client.embeddings.create(
        model="text-embedding-v3",    # 1536 维 embedding 模型
        input=text[:8000],             # 截断超长文本（API 限制 8000 字符）
    )
    # 返回的是 list[float]，长度 1536
    return response.data[0].embedding
```

#### 为什么用"发射后不管"模式？

向量索引不是关键路径——用户能收到 Agent 的回复就够了，向量化可以稍后慢慢做。所以这个函数：
- 用 `asyncio.create_task` 在后台跑（不 await）
- 异常只打日志，不上抛
- 失败了就失败，下次对话还能正常用

如果改成同步阻塞，用户每问一次都要等几百毫秒向量化完才能收到回复，体验会很差。

### 4.5 向量搜索实现

```python
# xiaopaw/skills/search_memory/scripts/search.py
"""search_memory 技能 —— 向量搜索历史对话。"""

import json
import os
import psycopg2                 # PostgreSQL 驱动
from typing import List, Dict


def search_memory(query: str, limit: int = 5) -> str:
    """搜索与 query 语义最相似的历史对话。

    流程：
    1. 把 query 转成向量
    2. 在 pgvector 中做余弦相似度搜索
    3. 返回最相似的 N 条记录
    """
    # 1. 读数据库连接串
    dsn = os.environ.get("MEMORY_DB_DSN")
    if not dsn:
        # 没配置数据库就返回错误（让 Agent 知道这个技能不可用）
        return json.dumps({"error": "MEMORY_DB_DSN not configured"})

    # 2. 把查询字符串转成向量
    # 注意这里是同步调用，因为是技能（在沙箱里跑）
    query_embedding = _get_embedding_sync(query)

    # 3. 连接数据库做向量搜索
    conn = psycopg2.connect(dsn)
    try:
        with conn.cursor() as cur:
            # ★ 核心 SQL：余弦相似度搜索
            # <=> 是 pgvector 的"余弦距离"操作符（值越小越相似）
            # 1 - (<=>) 转成"相似度"（值越大越相似，更直观）
            cur.execute("""
                SELECT user_message, assistant_reply, turn_ts,
                       1 - (embedding <=> %s::vector) as similarity
                FROM memory_vectors
                ORDER BY embedding <=> %s::vector
                LIMIT %s
            """, (query_embedding, query_embedding, limit))

            # 收集结果
            results = []
            for row in cur.fetchall():
                results.append({
                    "user_message": row[0],       # 历史用户消息
                    "assistant_reply": row[1],    # 历史 Agent 回复
                    "timestamp": row[2],          # 时间戳
                    "similarity": float(row[3]),   # 相似度分数（0~1）
                })
            # 返回 JSON 字符串（技能的统一返回格式）
            return json.dumps({"results": results}, ensure_ascii=False)
    finally:
        # ★ finally 保证连接一定被关闭
        # 即使中间抛异常也不会泄漏连接
        conn.close()
```

#### SQL 解读

```sql
SELECT user_message, assistant_reply, turn_ts,
       1 - (embedding <=> %s::vector) as similarity
FROM memory_vectors
ORDER BY embedding <=> %s::vector
LIMIT %s
```

- `embedding <=> %s::vector`：计算存储的向量和查询向量的"余弦距离"。值越小，两个向量越相似。
- `1 - (...)`：把"距离"转成"相似度"——距离 0 = 完全相似（相似度 1），距离 2 = 完全相反（相似度 -1）。
- `ORDER BY ... LIMIT N`：按距离升序排，取前 N 条（最相似的）。

### 4.6 函数详解：search_memory

| 项目 | 说明 |
|------|------|
| **参数** | `query: str` 查询文本；`limit: int = 5` 返回条数 |
| **返回值** | `str` JSON 字符串，格式 `{"results": [...]}` |
| **异常** | 数据库连接失败会抛 `psycopg2.OperationalError` |
| **调用方** | search_memory 技能（在沙箱里） |

**注意事项：**
1. `limit` 不要太大——返回太多会让 Agent 上下文爆炸，5 条够用了。
2. 相似度阈值要控制——低于 0.6 的结果通常是噪音，应该过滤掉。
3. 这个函数是同步的，因为沙箱里没有事件循环。在主进程里要用异步版本。

### 5.2 上下文压缩

```python
# xiaopaw/memory/context_mgmt.py
"""上下文管理 —— 压缩、剪枝、持久化。"""

def maybe_compress(
    messages: list[dict],          # 消息列表（会被原地修改）
    *,
    model_limit: int = 32000,      # 模型的 token 上限
    fresh_keep_turns: int = 10,    # 保留最近几轮不压缩
    chunk_tokens: int = 2000,
    compress_threshold: float = 0.45,   # 触发压缩的阈值（占上限的比例）
    compress_fn=None,              # 自定义压缩函数（默认是抽取式摘要）
) -> None:
    """当上下文接近 token 限制时压缩。

    策略：
    1. 估算当前 token 数
    2. 如果超过阈值的 45%，触发压缩
    3. 保留最近 10 轮完整对话
    4. 更早的对话摘要成一条 system 消息
    """
    # 1. 估算总 token 数
    total_tokens = count_tokens(messages)

    # 2. 没超阈值就返回，不压缩
    # 阈值默认 0.45（不是 0.8！）——留出余量，
    # 因为新增消息会持续增加 token，等到 80% 再压就来不及了
    if total_tokens < model_limit * compress_threshold:
        return

    # 3. 计算要保留的近期消息数（一轮 = user + assistant = 2 条）
    keep_count = fresh_keep_turns * 2
    if len(messages) <= keep_count:
        return  # 消息太少，不值得压缩

    # 4. 找到分割点
    split_idx = len(messages) - keep_count

    # 5. 保护 tool_calls 配对：
    # 如果分割点恰好把 tool 消息和它的 user 配对切断，
    # 往前回退到完整的 user 消息边界
    # （否则 LLM 会看到"孤儿 tool 消息"，会困惑）
    while split_idx > 0 and messages[split_idx - 1].get("role") != "user":
        split_idx -= 1

    if split_idx <= 0:
        return  # 找不到合适的分割点，放弃压缩

    # 6. 分割：早期消息 + 近期消息
    old_messages = messages[:split_idx]

    # 7. 摘要早期消息
    if compress_fn is None:
        summary = _default_compress(old_messages)   # 默认抽取式摘要
    else:
        summary = compress_fn(old_messages)          # 自定义摘要

    # 8. 用摘要替换早期消息（原地修改 messages）
    # ★ 这就是为什么参数是 list[dict] 而不是返回新列表——
    # 原地修改保证调用方拿到的还是同一个 list
    messages[:split_idx] = [
        {"role": "system", "content": f"[Earlier conversation summary]\n{summary}"}
    ]
    logger.info("compressed %d messages into summary (%d tokens saved)",
                len(old_messages), total_tokens - count_tokens(messages))


def _default_compress(messages: list[dict]) -> str:
    """简单抽取式摘要 fallback。

    为什么叫"抽取式"？
    因为它只是从原文里"抽取"片段，不重新生成。
    比 LLM 生成式摘要便宜（不调 LLM），但效果差。
    生产环境可以传入 compress_fn 用 LLM 摘要。
    """
    parts: list[str] = []
    for msg in messages:
        role = msg.get("role", "")
        content = msg.get("content", "")
        # 只保留 user 和 assistant 的消息（过滤 tool 消息）
        # 每个 content 截断到 200 字以内
        if role in ("user", "assistant") and content:
            parts.append(f"{role}: {content[:200]}")
    # 只保留最后 10 段（更早的太旧了，不重要）
    return "\n".join(parts[-10:])
```

#### 压缩策略通俗解释

想象你在写一篇长篇小说，写到第 50 章时发现稿纸快用完了。你有两个选择：

1. **保留最近 10 章的完整草稿**（fresh_keep_turns = 10）——这是近期情节，必须完整。
2. **把前 40 章压缩成一段"前情提要"**——只保留要点。

这样既省纸（token），又能继续往下写。`maybe_compress` 干的就是这件事。

### 5.3 工具结果剪枝

```python
def prune_tool_results(messages: list[dict], keep_turns: int = 10) -> None:
    """剪枝工具结果 —— 保留最近 N 轮的完整结果。

    工具结果（如搜索结果）往往很长（几千字），
    但早期结果通常不再需要完整保留。
    """
    # 消息太少就不剪枝
    if len(messages) <= keep_turns * 2:
        return

    # 找到"保留边界"——前面的都剪枝
    cutoff = len(messages) - keep_turns * 2

    # 遍历前面的消息，只剪 tool 类型的（user/assistant 不动）
    for i in range(cutoff):
        msg = messages[i]
        if msg.get("role") == "tool":
            content = msg.get("content", "")
            # 只剪超过 200 字的（短的留着不亏）
            if len(content) > 200:
                # 保留前 100 字 + 省略提示
                # 为什么不保留尾部？因为头部通常是结果摘要，更有用
                messages[i] = {**msg, "content": content[:100] + "... [pruned]"}
```

#### 为什么要单独剪 tool 结果？

因为 tool 结果（搜索结果、文件内容）是上下文里最长的部分。一条百度搜索结果可能有 5000 字，10 条就 50000 字，直接撑爆 context window。但早期工具结果通常不再需要——比如 5 轮前你搜的"Python 教程"，现在用户问"下一步怎么做"，那段搜索结果完全没用。

剪掉它能省下大量 token，又不损失重要信息（user/assistant 消息都保留）。

### 5.4 会话持久化

```python
def save_session_ctx(session_id: str, messages: list[dict], ctx_dir: Path) -> None:
    """保存会话上下文到文件。

    下次会话恢复时读取这个文件。
    """
    # 确保目录存在
    ctx_dir.mkdir(parents=True, exist_ok=True)

    # 文件名格式：{session_id}_ctx.json
    ctx_path = ctx_dir / f"{session_id}_ctx.json"

    # ★ "原子写"模式：先写临时文件，再 rename
    # 为什么这么做？如果直接 write_text 写到目标文件，
    # 写到一半进程崩了，会留下半截损坏的 JSON，下次读取会失败
    # 用临时文件 + rename，要么完整写入要么完全不写，不会留下损坏文件
    tmp = ctx_path.with_suffix(".tmp")
    tmp.write_text(json.dumps(messages, ensure_ascii=False), encoding="utf-8")
    tmp.rename(ctx_path)


def load_session_ctx(session_id: str, ctx_dir: Path) -> list[dict]:
    """从文件加载会话上下文。"""
    ctx_path = ctx_dir / f"{session_id}_ctx.json"
    if not ctx_path.exists():
        return []   # 新会话，没有历史上下文
    try:
        return json.loads(ctx_path.read_text(encoding="utf-8"))
    except (json.JSONDecodeError, OSError):
        # 文件损坏也不要崩，返回空列表（最坏降级为"无历史"）
        logger.warning("failed to load ctx for %s", session_id)
        return []


def append_session_raw(session_id: str, messages: list[dict], ctx_dir: Path) -> None:
    """追加保存原始消息到 JSONL 文件。

    为什么用 JSONL 而不是 JSON？
    JSONL = JSON Lines，每行一个 JSON。
    优点：可以一行一行追加，不用读整个文件再写回。
    """
    ctx_dir.mkdir(parents=True, exist_ok=True)
    raw_path = ctx_dir / f"{session_id}_raw.jsonl"
    with raw_path.open("a", encoding="utf-8") as f:
        for msg in messages:
            f.write(json.dumps(msg, ensure_ascii=False) + "\n")
```

## 七、设计优势与局限性

### 优势

1. **分层设计**：每层记忆有明确职责，不会互相干扰
2. **自动 + 手动结合**：Bootstrap 自动注入，File Memory 手动触发
3. **语义搜索**：向量记忆支持模糊匹配，找"相关的"而不是"精确的"
4. **自动压缩**：长对话不会超出 token 限制

### 局限性

1. **依赖外部服务**：向量搜索需要 PostgreSQL + pgvector
2. **Embedding 成本**：每次索引都消耗 API 调用
3. **权限敏感**：文件记忆的权限问题是最常见的坑
4. **记忆冲突**：三层记忆可能给出矛盾信息（如 user.md 和 memory.md 说的不一致）

## 九、常见问题

### ❓ 1. memory-save 说"已记住"但下次会话不记得，怎么办？

这是典型的"权限问题"。按以下顺序排查：

1. **查文件权限**：`ls -la data/workspace/*.md`，应该是 `-rw-rw-rw-` (666)
2. **查目录权限**：`ls -ld data/workspace`，应该是 `drwxrwxrwx` (777)
3. **查沙箱能写**：`docker exec xiaopaw-sandbox bash -c "echo test > /workspace/test.md"`
4. **查 trace**：去 Langfuse 看 memory-save 那一步的 stderr 有没有 `PermissionError`

### ❓ 2. memory.md 一直被截断怎么办？

说明 memory.md 太长了。两个办法：

1. **定期归档**：把旧的 memory.md 内容移到 `memory_archive_2024.md`，memory.md 只保留最近一个月
2. **提高 hard_limit**：改 `MemoryConfig.hard_limit_lines = 500`（但要小心 token 爆炸）

### ❓ 3. 向量搜索召回的相关度很低，怎么回事？

可能的原因：

1. **embedding 模型不对**：必须用 `text-embedding-v3`（1536 维），换模型维度对不上会报错
2. **数据太少**：刚部署时数据库空，召回质量差，等积累几轮对话后会好转
3. **相似度阈值没设**：低于 0.6 的结果应该过滤掉（在 search_memory 里加 `WHERE 1 - (embedding <=> %s) > 0.6`）
4. **session_id 过滤太严**：跨会话搜索时不要按 session_id 过滤

### ❓ 4. Bootstrap 注入后 token 太多怎么办？

四个文件加起来超长时：
- 精简 soul.md（核心人格保留，删掉冗余描述）
- user.md 只保留关键偏好（删掉过时信息）
- agent.md 合并重复规则
- memory.md 自动截断（已经处理）

### ❓ 5. 向量搜索和 search_memory 技能是什么关系？

`search_memory` 是给 Agent 调用的技能（封装在沙箱里跑），它内部调用向量搜索。Agent 自己不会直接写 SQL，而是通过这个技能间接查询。

### ❓ 6. 压缩后 Agent "忘了"早期对话怎么办？

这是必然的——压缩就是"丢细节保要点"。缓解办法：
1. 把重要信息用 memory-save 存到 user.md（这样 Bootstrap 会每次注入）
2. 调大 `fresh_keep_turns`（保留更多近期消息）
3. 用自定义 `compress_fn` 让 LLM 生成更精准的摘要

### ❓ 7. 三个 .md 文件之间有冲突怎么办？

比如 user.md 写"Python 初学者"，memory.md 写"用户已掌握 asyncio"。Agent 会困惑。处理原则：
- **user.md 优先**：它是"权威画像"，发现冲突时以它为准
- **memory.md 是观察**：它是"积累的事实"，可能过时
- **手动维护**：发现矛盾时用 memory-save 更新 user.md，覆盖旧信息
