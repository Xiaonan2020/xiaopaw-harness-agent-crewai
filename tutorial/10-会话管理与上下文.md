# 10 - 会话管理与上下文

## 一、会话管理概述

### 1.1 本节学习目标

读完本章你应该能回答：
- 什么是"会话"？为什么需要单独管理它？
- SessionManager 维护的是什么映射关系？为什么用 routing_key 而不是 user_id？
- 会话历史用什么格式存储？为什么选 JSONL 而不是 JSON？
- 上下文压缩在什么时候触发？策略是什么？

### 1.2 为什么需要会话管理？

LLM 是无状态的——它只看你这次传进去的 prompt。要让它"记住"上下文，必须由外部系统把历史消息拼回 prompt。这个外部系统就是会话管理。

```
用户：你好                      ← 第 1 轮
Agent：你好！有什么可以帮你的？
用户：帮我搜索 Python 新特性     ← 第 2 轮
Agent：[搜索结果] Python 3.12 引入了...
用户：详细说说第一条             ← 第 3 轮（需要第 2 轮的上下文）
```

如果没有会话管理，Agent 在第 3 轮时根本不知道"第一条"指什么——它只看到这一条消息，前面的搜索结果它完全不知道。

### 1.3 类比：会话管理 = "对话记录本"

把 SessionManager 想象成一个"对话记录本"：
- **每条消息进来**：在本子上记一行（append）
- **下次用户继续聊**：翻到本子的对应页（load_history）
- **本子太满**：把旧页摘要成一页（maybe_compress）
- **用户开新话题**：换一页新纸（create_new_session）
- **重启服务**：本子里的内容不丢，能继续翻（持久化到磁盘）

### 1.4 会话状态模型

```python
# xiaopaw/session/models.py
"""会话数据模型。"""

from __future__ import annotations

import uuid                              # 生成唯一 ID
from dataclasses import dataclass, field  # 数据类装饰器
from datetime import datetime, timezone   # 时间处理


def _new_session_id() -> str:
    """生成会话 ID：s- + 12 位 uuid hex。
    为什么加 s- 前缀？让 ID 一眼能看出是 session（区分于 message id 等）。
    """
    return f"s-{uuid.uuid4().hex[:12]}"


def _now_iso() -> str:
    """返回当前 UTC 时间的 ISO 格式字符串。"""
    return datetime.now(timezone.utc).isoformat()


@dataclass(frozen=True)   # frozen=True：实例不可变，线程安全
class MessageEntry:
    """单条消息记录。

    frozen=True 的好处：
    - 创建后不能修改，避免误操作改坏历史
    - 可以作为 dict 的 key（hashable）
    - 跨线程传递更安全
    """
    role: str                            # "user" 或 "assistant"
    content: str                         # 消息内容
    ts: int                              # 时间戳（毫秒）
    feishu_msg_id: str | None = None     # 飞书消息 ID（可选，用于回调）


@dataclass(frozen=True)
class SessionEntry:
    """会话实体。

    注意：这里没有 routing_key 字段——routing_key 在 RoutingEntry 里维护，
    SessionEntry 本身只关心"这个会话内部的状态"。
    这种设计让 SessionEntry 可以独立持久化。
    """
    id: str = field(default_factory=_new_session_id)   # 默认用 _new_session_id 生成
    created_at: str = field(default_factory=_now_iso)
    verbose: bool = False                # 详细模式（/verbose on）
    message_count: int = 0               # 消息计数


@dataclass
class RoutingEntry:
    """路由条目——一个 routing_key 下的所有会话。

    为什么一个 routing_key 对应多个会话？
    因为用户可能用 /new 开过新会话，旧会话还在（用于审计），
    但只有 active_session_id 指向的那个是"当前活跃"的。
    """
    active_session_id: str = ""          # 当前活跃会话 ID
    sessions: list[SessionEntry] = field(default_factory=list)   # 历史所有会话
```

#### 为什么用 dataclass(frozen=True)？

| 特性 | 普通 class | dataclass | frozen dataclass |
|------|-----------|-----------|------------------|
| 自动生成 __init__ | 否 | 是 | 是 |
| 自动生成 __repr__ | 否 | 是 | 是 |
| 可修改字段 | 是 | 是 | 否 |
| 可哈希（当 dict key） | 否 | 否 | 是 |
| 线程安全 | 否 | 否 | 是 |

MessageEntry 用 frozen=True 是因为：它一旦写入就不应该被改（历史记录不可篡改），而且可能被放进 set/dict 用于去重。

## 二、SessionManager 实现

### 2.1 本节学习目标

### 2.2 核心结构

```python
# xiaopaw/session/manager.py
"""Session manager: index.json + JSONL per-session storage."""

from __future__ import annotations

import asyncio                     # 异步 IO
import json                        # JSON 读写
import logging                     # 日志
from dataclasses import asdict, replace  # asdict: dataclass→dict；replace: 创建副本并改字段
from pathlib import Path

from xiaopaw.session.models import MessageEntry, RoutingEntry, SessionEntry

logger = logging.getLogger(__name__)

_LRU_MAX = 1000   # 每个 SessionManager 最多缓存 1000 个 session 锁


class _LRULockCache:
    """Bounded LRU cache for per-session asyncio.Lock instances.

    LRU = Least Recently Used（最近最少使用），
    当缓存满了，淘汰最久没用的那个。

    为什么要给每个 session 单独一把锁？
    - 如果全局一把锁，所有 session 的写操作都会串行，性能差
    - 如果每个 session 一把锁，不同 session 可以并发，相同 session 串行
    - 这就是"细粒度锁"模式
    """

    def __init__(self, maxsize: int = _LRU_MAX) -> None:
        self._maxsize = maxsize
        # 用 dict 模拟 LRU：Python 3.7+ 的 dict 保持插入顺序，
        # 访问时把 key 移到末尾（"最新使用"），淘汰时删开头（"最久没用"）
        self._cache: dict[str, asyncio.Lock] = {}

    def get(self, key: str) -> asyncio.Lock:
        """获取或创建 key 对应的锁。"""
        # 命中：先 pop 再放回末尾（实现"移到最新"）
        if key in self._cache:
            lock = self._cache.pop(key)   # 先删
            self._cache[key] = lock       # 再插到末尾
            return lock

        # 未命中且缓存满了：淘汰头部（最老的）
        if len(self._cache) >= self._maxsize:
            oldest = next(iter(self._cache))   # 拿到第一个 key
            del self._cache[oldest]            # 删掉

        # 创建新锁并放入末尾
        lock = asyncio.Lock()
        self._cache[key] = lock
        return lock


class SessionManager:
    """会话管理器。

    职责：
    1. 维护 routing_key → Session 映射
    2. 持久化会话历史到磁盘
    3. 支持创建新会话（/new 命令）
    4. 限制最大并发会话数
    """

    def __init__(self, data_dir: Path, max_active_sessions: int = _LRU_MAX) -> None:
        # 转成 Path 对象（如果是字符串路径会自动转换）
        self._data_dir = Path(data_dir)
        # 会话历史文件目录：data/sessions/
        self._sessions_dir = self._data_dir / "sessions"
        # 创建目录（parents=True 递归创建，exist_ok=True 已存在不报错）
        self._sessions_dir.mkdir(parents=True, exist_ok=True)
        # 索引文件路径：data/sessions/index.json
        self._index_path = self._sessions_dir / "index.json"
        # 索引锁：保护 index.json 的读写
        self._index_lock = asyncio.Lock()
        # 每个 session 一把锁的缓存（写 JSONL 时用）
        self._jsonl_locks = _LRULockCache(maxsize=max_active_sessions)
        # 内存中的索引：routing_key → RoutingEntry
        self._index: dict[str, RoutingEntry] = {}
        # 启动时从磁盘加载索引
        self._load_index()

    def _load_index(self) -> None:
        """从磁盘加载索引到内存。"""
        if not self._index_path.exists():
            return  # 首次启动，没有索引文件
        raw = json.loads(self._index_path.read_text(encoding="utf-8"))
        # 把 dict 反序列化成 RoutingEntry 对象
        for rk, entry in raw.items():
            sessions = [SessionEntry(**s) for s in entry.get("sessions", [])]
            self._index[rk] = RoutingEntry(
                active_session_id=entry["active_session_id"],
                sessions=sessions,
            )

    def _save_index(self) -> None:
        """把内存中的索引写到磁盘。

        ★ 用"原子写"：先写 .tmp 再 rename
        防止写到一半进程崩了，留下损坏的 index.json
        """
        data = {}
        for rk, entry in self._index.items():
            data[rk] = {
                "active_session_id": entry.active_session_id,
                "sessions": [asdict(s) for s in entry.sessions],  # asdict 把 dataclass 转成 dict
            }
        tmp = self._index_path.with_suffix(".tmp")
        tmp.write_text(json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8")
        tmp.rename(self._index_path)   # rename 是原子操作（POSIX）
```

#### 核心结构详解

**字段说明：**

| 字段 | 类型 | 作用 |
|------|------|------|
| `_data_dir` | `Path` | 数据根目录 |
| `_sessions_dir` | `Path` | 会话文件目录（`data/sessions/`） |
| `_index_path` | `Path` | 索引文件路径 |
| `_index_lock` | `asyncio.Lock` | 保护 `_index` 字典的并发读写 |
| `_jsonl_locks` | `_LRULockCache` | 每个 session 一把锁，细粒度并发控制 |
| `_index` | `dict[str, RoutingEntry]` | 内存中的索引：routing_key → 路由条目 |

**为什么用两把锁？**

- `_index_lock` 是"全局锁"——保护索引字典。索引操作很快（内存读写），所以全局锁不会成为瓶颈。
- `_jsonl_locks` 是"每 session 一把锁"——保护单个 session 的 JSONL 文件。文件 IO 慢，如果全局一把锁，多个 session 同时写文件会串行等待，所以按 session 加锁让它们能并发。

### 2.3 获取或创建会话

```python
    async def get_or_create(self, routing_key: str) -> SessionEntry:
        """获取或创建会话。

        如果 routing_key 已有活跃会话，返回该会话；
        否则创建新会话。

        【输入→处理→输出】
        输入：routing_key (str) - 路由键
        处理：先查索引，有就返回，没就创建
        输出：SessionEntry 对象
        """
        async with self._index_lock:        # 拿索引锁（保证 _index 操作原子）
            entry = self._index.get(routing_key)
            # 找到活跃会话就返回
            if entry and entry.active_session_id:
                for s in entry.sessions:
                    if s.id == entry.active_session_id:
                        return s
            # 没有就创建（已在锁内）
            return await self._create_session_locked(routing_key)
```

#### 输入→处理→输出 示例

```
输入：routing_key = "p2p:ou_abc123"
   ↓
处理：
  1. 加 _index_lock
  2. 查 _index["p2p:ou_abc123"]
  3. 找到 RoutingEntry，里面有 active_session_id = "s-abc123def456"
  4. 遍历 sessions 找到 id 匹配的 SessionEntry
   ↓
输出：SessionEntry(id="s-abc123def456", created_at="2024-01-15T...", message_count=12)

如果 routing_key 不存在：
   ↓
处理：调用 _create_session_locked 创建新会话
   ↓
输出：新创建的 SessionEntry
```

### 2.4 创建新会话（/new 命令）

```python
    async def create_new_session(self, routing_key: str) -> SessionEntry:
        """显式创建新会话（/new 命令）。

        旧会话的历史不会删除，但 routing_key 指向新会话。
        也就是说，旧的 .jsonl 文件还在磁盘上（可以审计），
        但 routing_key 现在指向新的 session_id。

        【输入→处理→输出】
        输入：routing_key (str)
        处理：无视现有活跃会话，直接创建新的
        输出：新 SessionEntry
        """
        async with self._index_lock:
            return await self._create_session_locked(routing_key)

    async def _create_session_locked(self, routing_key: str) -> SessionEntry:
        """实际创建会话（必须在 _index_lock 内调用）。"""
        # 创建 SessionEntry，由于有 default_factory，会自动生成 id 和 created_at
        session = SessionEntry()

        entry = self._index.get(routing_key)
        if entry:
            # 已有 routing_key：把新会话追加到 sessions 列表
            # active_session_id 指向新会话（旧的还在 sessions 里但不再活跃）
            sessions = list(entry.sessions) + [session]
            self._index[routing_key] = RoutingEntry(
                active_session_id=session.id, sessions=sessions
            )
        else:
            # 全新 routing_key：创建 RoutingEntry
            self._index[routing_key] = RoutingEntry(
                active_session_id=session.id, sessions=[session]
            )
        # 立刻持久化索引（防止重启丢失）
        self._save_index()
        logger.info("created session %s for %s", session.id, routing_key)
        return session
```

#### /new 命令的效果

```
执行 /new 前：
  _index["p2p:ou_abc"] = RoutingEntry(
      active_session_id="s-old123",
      sessions=[SessionEntry(id="s-old123", ...)]
  )

执行 /new 后：
  _index["p2p:ou_abc"] = RoutingEntry(
      active_session_id="s-new456",        ← 指向新会话
      sessions=[
          SessionEntry(id="s-old123", ...), ← 旧会话还在（用于审计）
          SessionEntry(id="s-new456", ...), ← 新会话
      ]
  )

磁盘上：
  data/sessions/s-old123.jsonl  ← 旧会话历史保留
  data/sessions/s-new456.jsonl   ← 新会话从空开始
```

### 2.5 追加会话历史

```python
    async def append(
        self,
        session_id: str,
        *,
        user: str,                    # 用户消息
        feishu_msg_id: str | None = None,  # 飞书消息 ID（可选）
        assistant: str,               # Agent 回复
        ts: int = 0,                  # 时间戳（毫秒）
    ) -> None:
        """追加一条对话记录（user + assistant 两条）。

        【输入→处理→输出】
        输入：session_id + user 消息 + assistant 回复
        处理：构造两条 MessageEntry，追加到 JSONL 文件
        输出：无（修改文件 + 更新内存计数）
        """
        # 1. 拿到这个 session 专属的锁
        lock = self._jsonl_locks.get(session_id)
        async with lock:                # 同一 session 的写入串行
            jsonl_path = self._sessions_dir / f"{session_id}.jsonl"

            # 2. 构造两条消息记录
            user_entry = MessageEntry(
                role="user", content=user, ts=ts, feishu_msg_id=feishu_msg_id
            )
            asst_entry = MessageEntry(role="assistant", content=assistant, ts=ts)

            # 3. 写入文件（在子线程里执行，不阻塞事件循环）
            def _write() -> None:
                # "a" 模式 = append（追加，不覆盖）
                with jsonl_path.open("a", encoding="utf-8") as f:
                    # 每条消息写一行（JSONL 格式）
                    f.write(json.dumps(asdict(user_entry), ensure_ascii=False) + "\n")
                    f.write(json.dumps(asdict(asst_entry), ensure_ascii=False) + "\n")

            # asyncio.to_thread 把同步函数丢到线程池里跑
            await asyncio.to_thread(_write)

        # 4. 更新消息计数（要拿 _index_lock，因为 _index 是共享的）
        async with self._index_lock:
            entry = self._index.get("")
            for rk, re_ in self._index.items():
                if re_.active_session_id == session_id:
                    # 用 replace 创建副本并修改 message_count
                    # 不能直接改，因为 SessionEntry 是 frozen 的
                    sessions = [
                        replace(s, message_count=s.message_count + 2)
                        if s.id == session_id
                        else s
                        for s in re_.sessions
                    ]
                    self._index[rk] = replace(re_, sessions=sessions)
                    self._save_index()
                    break
```

#### 为什么用 asyncio.to_thread？

文件 IO 是同步操作（`f.write` 会阻塞）。如果在 async 函数里直接写，会阻塞整个事件循环——其他协程（比如另一个用户的请求）都得等。

`asyncio.to_thread(_write)` 把 `_write` 丢到线程池里执行，主协程 `await` 它时事件循环可以继续跑别的协程。这是"用线程池跑同步 IO"的标准做法。

### 2.6 加载历史

```python
    async def load_history(
        self, session_id: str, max_turns: int = 20
    ) -> list[MessageEntry]:
        """加载会话历史。

        从 JSONL 文件逐行读取，返回 MessageEntry 列表。

        【输入→处理→输出】
        输入：session_id, max_turns (最多返回多少轮)
        处理：读 JSONL 文件 → 解析每行 → 截取最后 N 轮
        输出：list[MessageEntry]
        """
        jsonl_path = self._sessions_dir / f"{session_id}.jsonl"
        if not jsonl_path.exists():
            return []   # 新会话，没历史

        def _read() -> list[MessageEntry]:
            # 一次读完整个文件（按 \n 分割成行列表）
            # 对于不太大的会话文件这是合理的
            lines = jsonl_path.read_text(encoding="utf-8").strip().split("\n")
            entries: list[MessageEntry] = []
            for line in lines:
                if not line.strip():
                    continue   # 跳过空行
                data = json.loads(line)
                if "role" in data:
                    entries.append(MessageEntry(**data))
            # 只保留最后 max_turns * 2 条（一轮 = user + assistant = 2 条）
            tail = max_turns * 2
            return entries[-tail:] if len(entries) > tail else entries

        # 在子线程里读文件
        return await asyncio.to_thread(_read)
```

#### 为什么默认 max_turns=20？

如果会话有 100 轮，全加载进来会拼成超长 prompt，撑爆 context window。所以默认只取最后 20 轮（40 条消息）。早期对话如果想保留，靠 maybe_compress 摘要成 system 消息。

### 2.7 会话信息查询

```python
    def get_session_info(self, routing_key: str) -> SessionEntry | None:
        """获取会话摘要信息（/status 命令用）。

        【输入→处理→输出】
        输入：routing_key
        处理：查 _index 找到活跃 SessionEntry
        输出：SessionEntry 或 None（routing_key 不存在时）

        注意：这是同步方法（不需要 await），因为只读内存索引。
        """
        entry = self._index.get(routing_key)
        if not entry:
            return None
        for s in entry.sessions:
            if s.id == entry.active_session_id:
                return s
        return None

    async def clear_all(self) -> None:
        """清空所有会话（开发调试用，慎用！）。"""
        async with self._index_lock:
            self._index.clear()
            self._save_index()
```

### 2.8 update_verbose 方法

```python
    async def update_verbose(self, routing_key: str, verbose: bool) -> None:
        """切换详细模式（/verbose on|off）。

        【输入→处理→输出】
        输入：routing_key, verbose (True/False)
        处理：找到活跃 SessionEntry，用 replace 创建副本并改 verbose 字段
        输出：无（更新 _index 并持久化）
        """
        async with self._index_lock:
            entry = self._index.get(routing_key)
            if not entry:
                return   # routing_key 不存在，啥也不做
            # 用 replace 改 verbose 字段（因为 SessionEntry 是 frozen 的）
            sessions = [
                replace(s, verbose=verbose) if s.id == entry.active_session_id else s
                for s in entry.sessions
            ]
            self._index[routing_key] = replace(entry, sessions=sessions)
            self._save_index()
```

## 三、上下文恢复机制

### 3.1 本节学习目标

- 看懂 `_restore_session` 怎么把历史消息"塞回"上下文
- 理解为什么要把历史 system 消息过滤掉

### 3.2 恢复流程

```python
# xiaopaw/agents/main_crew.py 的 _restore_session 方法
def _restore_session(self, context: LLMCallHookContext) -> None:
    """从持久化存储恢复会话历史到 LLM 上下文。

    流程：
    1. 从 ctx_dir 读取保存的消息列表
    2. 分离当前 system 消息和最新 user 消息
    3. 把历史消息插入中间

    消息结构变化：
    恢复前：[system, user_current]
    恢复后：[system, hist_msg1, hist_msg2, ..., user_current]
    """
    # 从磁盘读取上次保存的完整上下文
    history = load_session_ctx(self.session_id, ctx_dir=self._ctx_dir)
    if not history:
        return   # 新会话，没有历史上下文，啥也不做

    # 1. 分离当前的 system 消息（这个要保留，是本次的 Bootstrap）
    current_system_msgs = [m for m in context.messages if m.get("role") == "system"]

    # 2. 找到当前的最新 user 消息（要放在最末尾）
    current_user_msg = None
    # 倒序遍历，找到第一个 role=user 的消息
    for m in reversed(context.messages):
        if m.get("role") == "user":
            current_user_msg = m
            break

    # 3. 过滤历史中的 system 消息
    # 为什么要过滤？因为历史的 system 是上次的 Bootstrap，
    # 这次已经有新的 system 了，不能让两个 system 冲突
    hist_conv = [m for m in history if m.get("role") != "system"]

    # 4. 记录历史长度（保存增量时用得到）
    # _history_len 用来标记"上次保存到哪了"，下次只保存新增部分
    self._history_len = len(current_system_msgs) + len(hist_conv)

    # 5. 重组消息列表
    # 顺序：system（本次 Bootstrap）→ 历史对话 → 当前 user 消息
    context.messages.clear()                          # 先清空
    context.messages.extend(current_system_msgs)     # system 在最前
    context.messages.extend(hist_conv)                # 历史对话放中间
    if current_user_msg:
        context.messages.append(current_user_msg)    # 最新 user 消息在最后
```

#### 消息列表变化前后对比

**恢复前（context.messages 初始状态）：**

```
[
  {role: "system", content: "<soul>...</soul><user>...</user>"},  ← 本次 Bootstrap
  {role: "user", content: "详细说说第一条"}                        ← 本轮用户消息
]
```

**恢复后（context.messages 重组后）：**

```
[
  {role: "system", content: "<soul>...</soul><user>...</user>"},  ← 本次 Bootstrap（保留）
  {role: "user", content: "帮我搜索 Python 新特性"},              ← 历史第 2 轮
  {role: "assistant", content: "Python 3.12 引入了..."},          ← 历史第 2 轮回复
  {role: "user", content: "详细说说第一条"}                        ← 本轮用户消息（在最后）
]
```

注意：历史的 system 消息被过滤掉了（避免和本次 Bootstrap 冲突），current_user_msg 被移到末尾（LLM 看到最新的输入在最下面）。

### 3.3 保存增量

```python
# run_and_index 方法中
async def run_and_index(self) -> str:
    result = await self.crew().akickoff(...)

    # ★ 保存新增的消息（增量保存）
    # _last_msgs 是本次 LLM 看到的所有消息（恢复后的完整列表）
    # _history_len 是恢复时的历史长度
    # 两者之差就是本次新增的消息
    new_msgs = self._last_msgs[self._history_len:] if self._last_msgs else []

    # 追加到原始消息文件（JSONL 格式，append 模式）
    append_session_raw(self.session_id, new_msgs, self._ctx_dir)

    # 保存完整上下文（下次恢复用）
    # 这是"全量保存"——下次恢复时直接读这个文件
    save_session_ctx(self.session_id, list(self._last_msgs), self._ctx_dir)

    return reply
```

#### 为什么既存 raw 又存 ctx？

- `*_raw.jsonl`：追加模式，只增不减。完整保留所有历史消息（包括被压缩过的）。用于审计和回放。
- `*_ctx.json`：全量保存当前 LLM 看到的消息列表（已压缩）。用于下次恢复时直接读。

两者分工不同：raw 是"事实记录"（不可篡改），ctx 是"工作快照"（可能被压缩改写）。

## 四、上下文压缩详解

### 4.1 本节学习目标

- 看懂 `maybe_compress` 的完整策略
- 理解触发条件、压缩点选择、摘要生成
- 知道压缩前后消息列表的变化

### 4.2 压缩策略

```python
# xiaopaw/memory/context_mgmt.py

def maybe_compress(
    messages: list[dict],
    *,
    model_limit: int = 32000,        # 模型 token 上限
    fresh_keep_turns: int = 10,      # 保留最近 N 轮不压缩
    chunk_tokens: int = 2000,
    compress_threshold: float = 0.45,   # 触发阈值（占上限的比例）
    compress_fn=None,                # 自定义压缩函数
) -> None:
    """上下文压缩 —— 超限时摘要早期对话。

    压缩策略：
    1. 估算当前 token 总数
    2. 超过 model_limit 的 45% 时触发
    3. 保留最近 10 轮完整对话
    4. 更早的对话用摘要替换

    消息结构变化：
    压缩前：[sys, u1, a1, u2, a2, ..., u20, a20, u21, ...]
    压缩后：[sys, <summary>, u12, a12, ..., u21, ...]
    """
    # 1. 估算总 token 数
    total_tokens = count_tokens(messages)

    # 2. 触发判断
    # ★ 注意阈值是 0.45，不是 0.8！
    # 为什么？因为：
    # - 用户每发一条消息，token 会继续涨
    # - 如果到 80% 才压，下一轮用户消息就可能撑爆
    # - 45% 就压，留出 55% 余量给后续对话
    if total_tokens < model_limit * compress_threshold:
        return   # 没到阈值，不压缩

    # 3. 计算保留的近期消息数（一轮 = user + assistant = 2 条）
    keep_count = fresh_keep_turns * 2
    if len(messages) <= keep_count:
        return   # 消息太少，不值得压缩

    # 4. 找分割点：从末尾往前数 keep_count 条
    split_idx = len(messages) - keep_count

    # 5. 保护 tool_calls 配对
    # 如果分割点恰好落在 tool 消息和它的 user 之间，
    # 会留下"孤儿 tool 消息"（LLM 会困惑：哪来的 tool？）
    # 所以往前回退，直到上一个 user 消息的边界
    while split_idx > 0 and messages[split_idx - 1].get("role") != "user":
        split_idx -= 1

    if split_idx <= 0:
        return   # 找不到合适的分割点，放弃压缩

    # 6. 分割
    old_messages = messages[:split_idx]      # 要被压缩的早期消息

    # 7. 生成摘要
    if compress_fn is None:
        summary = _default_compress(old_messages)
    else:
        summary = compress_fn(old_messages)

    # 8. 原地替换：用摘要替换早期消息
    # messages[:split_idx] = [...] 是切片赋值，会替换那段
    messages[:split_idx] = [
        {"role": "system", "content": f"[Earlier conversation summary]\n{summary}"}
    ]
    logger.info("compressed %d messages into summary (%d tokens saved)",
                len(old_messages), total_tokens - count_tokens(messages))
```

#### 压缩流程图

```
触发：估算 token = 18000 > 32000 * 0.45 = 14400
   ↓
保留：fresh_keep_turns = 10，所以最后 20 条不压
   ↓
分割：找到第 N 条（N = 总数 - 20）
   ↓
检查：第 N-1 条是不是 user？不是就往前找
   ↓
摘要把 [m1, m2, ..., mN] 变成一条 system 消息
   ↓
替换：messages = [sys, <summary>, mN+1, ..., mLast]
   ↓
完成：token 从 18000 降到 ~7000
```

### 4.3 Token 估算

```python
# xiaopaw/memory/token_counter.py
"""Token 计数器。"""

import tiktoken   # OpenAI 的 token 计数库


def count_tokens(text, model: str = "qwen3-max") -> int:
    """估算文本的 token 数。

    对于 Qwen 系列，用 tiktoken 的 cl100k_base 近似计算。
    实际 token 数可能略有偏差，但足够用于触发压缩判断。
    """
    # 如果 text 是 messages 列表，累加每条消息的 token
    if isinstance(text, list):
        return sum(count_tokens(m.get("content", "")) for m in text if isinstance(m, dict))

    try:
        encoding = tiktoken.get_encoding("cl100k_base")
        return len(encoding.encode(text))
    except Exception:
        # 降级：粗略估算（4 字符 ≈ 1 token）
        # 这是英文的经验值，中文实际是 1.5 字符 ≈ 1 token
        # 但作为触发判断够用了
        return len(text) // 4
```

#### 为什么用近似估算？

精确 token 计数需要调用模型的 tokenizer，但 Qwen 的 tokenizer 不是 tiktoken 原生支持的。用 `cl100k_base`（GPT-4 的 tokenizer）近似，会有 5-10% 偏差。对于"是否触发压缩"这种判断，足够了——反正压缩阈值留了余量（45% 而不是 95%）。

### 4.4 工具结果剪枝

```python
def prune_tool_results(messages: list[dict], keep_turns: int = 10) -> None:
    """剪枝工具结果 —— 保留最近 N 轮的完整结果。

    工具结果（如搜索结果）往往很长，
    但早期结果通常不再需要完整保留。
    """
    # 消息太少不剪
    if len(messages) <= keep_turns * 2:
        return

    # 找到"保留边界"：前面的都剪
    cutoff = len(messages) - keep_turns * 2

    # 只剪 role=tool 或 role=function 的消息（user/assistant 不动）
    tool_indices = [
        i for i, m in enumerate(messages)
        if m.get("role") == "tool" or m.get("role") == "function"
    ]

    if len(tool_indices) <= keep_turns:
        return   # 工具消息不多，不剪

    # 截断早期的工具结果（保留尾部 keep_turns 个）
    indices_to_prune = tool_indices[:-keep_turns]
    for i in indices_to_prune:
        content = messages[i].get("content", "")
        if len(content) > 200:
            # 保留头尾各 100 字，中间省略
            messages[i]["content"] = (
                content[:100]
                + "\n...[pruned for length]...\n"
                + content[-100:]
            )
```

#### 为什么要单独剪 tool 结果？

工具结果（搜索结果、文件内容、API 响应）是上下文里最长的部分。一条搜索结果可能 5000 字，10 条就 50000 字，远超 context window。但早期工具结果通常不再需要——5 轮前搜的"Python 教程"，现在用户问"下一步"，那段结果完全没用。

剪掉它能省下大量 token，又不损失重要信息（user/assistant 消息都保留）。

```python
# xiaopaw/runner.py 的 _handle_slash 方法
async def _handle_slash(self, cmd: str, inbound: InboundMessage) -> str:
    """处理斜杠命令（不经过 Agent，直接返回）。

    为什么斜杠命令不走 Agent？
    因为这些是"系统指令"，不是"对话内容"。
    走 Agent 会浪费 LLM 调用，而且 LLM 可能误解命令。
    """
    key = inbound.routing_key

    if cmd == "/new":
        # 显式创建新会话
        session = await self._session_mgr.create_new_session(key)
        return f"已创建新会话 {session.id}"

    if cmd == "/help":
        return (
            "可用命令：\n"
            "  /new — 创建新会话\n"
            "  /status — 查看当前会话状态\n"
            "  /verbose on|off — 开关详细模式\n"
            "  /help — 显示此帮助"
        )

    if cmd == "/status":
        # 查询会话信息
        session_info = self._session_mgr.get_session_info(key)
        if session_info:
            return (
                f"会话 ID: {session_info.id}\n"
                f"创建时间: {session_info.created_at}\n"
                f"消息数: {session_info.message_count}"
            )
        return "当前无活动会话"

    if cmd == "/verbose":
        # 解析参数：/verbose on 或 /verbose off
        parts = inbound.content.strip().split()
        on = parts[1].lower() in ("on", "1", "true") if len(parts) > 1 else True
        await self._session_mgr.update_verbose(key, on)
        return f"详细模式已{'开启' if on else '关闭'}"

    return f"未知命令: {cmd}"
```

### 6.2 JSONL 格式

```jsonl

{"role":"assistant","content":"Python 3.12 的新特性包括...","ts":1704067290}
```

#### 为什么选 JSONL 而不是 JSON？

| 维度 | JSON | JSONL |
|------|------|-------|
| **结构** | 整个文件是一个 JSON | 每行一个独立 JSON |
| **追加写入** | 不行（要读全文件→改→写回） | 可以（直接 append 一行） |
| **读取方式** | 必须一次读完整个文件 | 可以一行一行读（流式） |
| **部分损坏** | 整个文件废了 | 只损坏的那行跳过，其他行还能用 |
| **大文件性能** | 慢（要全量解析） | 快（只读需要的行） |

**通俗类比**：JSON 像一本"装订好的书"，要改一个字得拆开重装；JSONL 像"活页笔记"，加一页直接夹进去就行。

会话历史是不断追加的（每轮对话都加 2 条），用 JSONL 最自然——直接 `f.write(... + "\n")` 就行。用 JSON 的话每次都要"读全文件→解析→改 list→序列化→写回"，又慢又容易出错。

## 七、设计优势与局限性

### 优势

1. **持久化**：重启后能恢复会话
2. **自动压缩**：长对话不会超出 token 限制
3. **增量保存**：只保存新增消息，效率高
4. **斜杠命令**：用户可直接控制会话
5. **细粒度锁**：每个 session 一把锁，并发性能好
6. **原子写**：索引和上下文都用 .tmp + rename，不会损坏

### 局限性

1. **单机存储**：会话数据在本地磁盘，不支持分布式
2. **无加密**：会话文件明文存储（生产环境需加密）
3. **压缩信息损失**：摘要可能丢失细节
4. **索引常驻内存**：session 数量极大时内存压力大（有 LRU 兜底）

## 九、常见问题

### ❓ 1. 重启服务后，会话历史还在吗？

在。`SessionManager.__init__` 会调 `_load_index` 从 `index.json` 恢复索引，`load_history` 从 `*.jsonl` 读历史。所有持久化都在磁盘上，重启不丢。

### ❓ 2. 为什么用 routing_key 而不是 user_id 作为索引键？

因为同一个用户在 p2p 和不同群里是不同会话。比如：
- `p2p:ou_abc` = 私聊会话
- `group:chat_xyz` = 群 A 的会话
- `group:chat_def` = 群 B 的会话

如果用 user_id，私聊和群聊会混在一起。用 routing_key（包含 chat 类型 + ID）能区分。

### ❓ 3. 上下文压缩后 Agent "忘了"早期对话怎么办？

这是必然的——压缩就是"丢细节保要点"。缓解办法：
1. 调大 `fresh_keep_turns`（保留更多近期消息）
2. 调低 `compress_threshold`（更早压缩，但摘要更短）
3. 用自定义 `compress_fn` 让 LLM 生成更精准的摘要
4. 把重要信息用 memory-save 存到 user.md（Bootstrap 每次注入）

### ❓ 4. 同一个 session 写入冲突怎么办？

不会冲突。`_jsonl_locks` 给每个 session 一把锁，同一 session 的写入会串行。不同 session 之间可以并发。

### ❓ 5. _restore_session 为什么把历史 system 消息过滤掉？

因为历史的 system 是上次的 Bootstrap（包含旧的人格/用户画像）。这次已经有新的 system 了，如果让两个 system 同时存在，LLM 会困惑（"听哪个？"）。所以只保留本次的 system，历史的过滤掉。

### ❓ 6. JSONL 文件越来越大怎么办？

两个办法：
1. **定期归档**：把超过 N 天的 .jsonl 移到 archive 目录
2. **限制 load_history 的 max_turns**：默认 20 轮，加载时只取尾部，不影响读取性能
3. **磁盘监控**：设置告警，单个 .jsonl 超过 10MB 时报警

### ❓ 7. /new 命令后旧会话的历史还能找回吗？

能。旧会话的 .jsonl 文件不会被删除，只是 routing_key 不再指向它。要找回：
1. 看 `index.json` 里那个 routing_key 的 `sessions` 列表
2. 找到旧 session_id
3. 直接读 `data/sessions/{旧 session_id}.jsonl`
