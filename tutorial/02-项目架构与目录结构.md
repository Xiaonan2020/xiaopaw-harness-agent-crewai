## 一、整体架构设计

### 1.1 分层架构

> 📖 **概念小课堂：什么是"分层架构"？**
>
> 想象一栋写字楼：1 楼是前台（接待访客），2 楼是行政（调度资源），3 楼是核心业务部门（写代码），4 楼是车间（实际动手）。每层只跟相邻楼层说话，不跨层喊话——这就是"分层"。
>
> 好处：换前台不影响业务部门；车间着火也烧不到前台。XiaoPaw 用的是"洋葱架构"——一层包一层，越内层越核心，外层依赖内层，内层不知道外层。

XiaoPaw 采用"洋葱架构"——从外到内层层包裹，每一层只依赖更内层的模块：

```text
┌─────────────────────────────────────────────────────────────┐
│                    接入层（Entry Layer）                      │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │ FeishuListener│  │   TestAPI    │  │   Cron       │      │
│  │  (WebSocket)  │  │  (HTTP API)  │  │  (定时任务)   │      │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘      │
│         └──────────────────┼──────────────────┘             │
└────────────────────────────┼────────────────────────────────┘
                             │  统一交给调度层处理
┌────────────────────────────┼────────────────────────────────┐
│                    调度层（Dispatch Layer）                  │
│                ┌───────────▼───────────┐                    │
│                │       Runner         │                    │
│                │  (消息队列 + Worker)  │                    │
│                └───────────┬───────────┘                    │
└────────────────────────────┼────────────────────────────────┘
                             │  分发给业务层处理
┌────────────────────────────┼────────────────────────────────┐
│                    业务层（Business Layer）                   │
│  ┌───────────┐  ┌──────────▼──────────┐  ┌──────────────┐    │
│  │  Memory   │  │     MainCrew       │  │   Session    │    │
│  │ (三层记忆) │  │   (Agent 编排)     │  │  (会话管理)   │    │
│  └───────────┘  └──────────┬──────────┘  └──────────────┘    │
│                            │                                 │
│                ┌───────────▼───────────┐                    │
│                │    SkillLoader       │                    │
│                │  (渐进式能力披露)      │                    │
│                └───────────┬───────────┘                    │
└────────────────────────────┼────────────────────────────────┘
                             │  把技能执行交给执行层
┌────────────────────────────┼────────────────────────────────┐
│                    执行层（Execution Layer）                  │
│                ┌───────────▼───────────┐                    │
│                │      SubCrew         │                    │
│                │    (沙箱执行)         │                    │
│                └───────────┬───────────┘                    │
│                            │                                 │
│                ┌───────────▼───────────┐                    │
│                │    AIO-Sandbox        │                    │
│                │   (Docker + MCP)      │                    │
│                └───────────────────────┘                    │
└─────────────────────────────────────────────────────────────┘
                             │
┌────────────────────────────┼────────────────────────────────┐
│                  横切层（Cross-cutting Layer）                │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐    │
│  │  Hooks   │  │ Config   │  │Observability│  │   LLM    │    │
│  │ (框架)   │  │ (Pydantic)│  │ (Metrics)  │  │ (接入)    │    │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘    │
└─────────────────────────────────────────────────────────────┘
```

**逐步解读：**

1. **接入层**：负责"听"——接收来自飞书（生产）、TestAPI（开发）、Cron（定时）的请求。三种入口都把请求转换成统一的 `InboundMessage` 格式交给下层。
2. **调度层**：负责"排队"——Runner 按用户 ID 分队列，保证同一用户的消息串行处理（不会两条消息同时跑导致上下文混乱）。
3. **业务层**：负责"思考"——MainCrew 是 AI 大脑，理解用户意图、选技能；Memory 提供历史记忆；Session 维护会话状态。
4. **执行层**：负责"动手"——SubCrew 在沙箱里跑代码，AIO-Sandbox 是真正的 Docker 容器。
5. **横切层**：像保安和会计一样贯穿所有层——Hooks 做安全检查、Config 提供配置、Observability 收集指标、LLM 接入大模型。

> 💡 **实际场景**：你打开飞书发"帮我搜 Python 3.13"。
> - 接入层 FeishuListener 听到消息 → 包装成 InboundMessage
> - 调度层 Runner 看到这是用户 ou_xxx 的消息 → 排进 ou_xxx 的队列
> - 业务层 MainCrew 思考 → "这是搜索需求，用 baidu_search"
> - 执行层 SubCrew 在沙箱里跑搜索代码 → 拿到结果
> - 横切层全程监控：日志记录、性能指标、安全检查

### 1.2 设计原则

> 📖 **概念小课堂：SOLID 设计原则**
>
> 这是面向对象编程的五大原则，XiaoPaw 用了其中三条。听起来高大上，其实都是"少踩坑"的常识。

1. **单一职责**：每个模块只做一件事
   - 类比：厨房里切菜的刀只切菜，不拿来开罐头——专业分工，维护方便。
2. **依赖倒置**：高层模块不依赖低层模块，都依赖抽象接口
   - 类比：插座和插头——电器（高层）和电厂（低层）都依赖"220V 标准接口"，谁都能换。
3. **开闭原则**：对扩展开放，对修改关闭（Hook 框架就是典型应用）
   - 类比：装修时不砸承重墙，加家具可以——核心不动，扩展方便。
4. **渐进式复杂度**：简单功能不需要理解全部细节
   - 类比：会开车不用懂发动机原理——只暴露必要接口。

## 三、各目录职责详解

### 3.1 `xiaopaw/` — 主代码

> 📖 **概念小课堂：什么是 `xiaopaw/` 子目录？**
>
> 这是项目的"业务核心区"——所有跟 XiaoPaw 业务相关的代码都在这。下面的子目录按"职责"划分，每个目录负责一块独立的功能。

这是项目的核心代码目录，包含所有业务逻辑：

| 子目录 | 职责 | 依赖方向 |
|--------|------|---------|
| `agents/` | 定义 Main Crew 和 Sub-Crew | → tools, memory, llm |
| `tools/` | 实现 SkillLoaderTool | → agents (skill_crew) |
| `skills/` | 13 个技能的 SKILL.md 和脚本 | 被沙箱读取 |
| `memory/` | 三层记忆实现 | → 数据库/文件系统 |
| `session/` | 会话状态管理 | → 文件系统 |
| `feishu/` | 飞书 SDK 封装 | → lark-oapi |
| `llm/` | LLM 接入 | → openai SDK |
| `config/` | 配置系统 | → pydantic |
| `hook_framework/` | Hook 框架核心 | 被 shared_hooks 使用 |
| `observability/` | 可观测性 | → prometheus_client |

> 💡 **实际场景**：你想加一个"图片识别"技能——
> 1. 在 `xiaopaw/skills/` 下建 `image_recognition/` 目录
> 2. 写 `SKILL.md` 描述技能
> 3. 写 `scripts/` 放识别脚本
> 4. 在 `xiaopaw/skills/load_skills.yaml` 里启用
> 不用动其他任何代码，SkillLoaderTool 会自动发现新技能。

### 3.2 `shared_hooks/` — 加固层

> 📖 **概念小课堂：为什么叫"加固层"？**
>
> 想象一栋楼的消防系统：洒水喷头、烟感器、报警器——它们独立于楼里的办公功能，但又在每个角落监督安全。`shared_hooks/` 就是 XiaoPaw 的"消防系统"，独立于业务代码，但贯穿所有业务流程。

这是系统加固的核心，包含 9 个策略：

```python
# 按功能分类：
# 观测层（dispatch，异常被吞，不影响业务）
# 类比：监控摄像头——坏了不影响办公，只是没录像
# ├── structured_log.py    → JSON 事件日志
# └── langfuse_trace.py    → Langfuse 全链路追踪

# 安全层（dispatch_gate，可阻断业务）
# 类比：安检门——发现违禁品就拦下你
# ├── sandbox_guard.py     → 输入消毒（路径穿越/Shell注入/Prompt注入）
# ├── permission_gate.py   → 工具权限控制
# └── audit_logger.py      → 审计日志

# 可靠性层（dispatch_gate，可阻断业务）
# 类比：保险丝——超载就断电保护
# ├── cost_guard.py        → 成本围栏（$1 上限）
# ├── loop_detector.py     → 循环检测（阈值 3）
# └── retry_tracker.py     → 重试追踪（最多 5 次）
```

> 💡 **实际场景**：用户让 AI 一直做同一件事（卡死了循环）。`loop_detector.py` 检测到这个技能在 3 轮内被重复调用——直接阻断，回复"检测到循环，已停止"。防止烧 token。

### 3.3 `workspace-init/` — 记忆四件套模板

> 📖 **概念小课堂：为什么要有"模板"？**
>
> 新用户第一次和 XiaoPaw 对话时，AI 需要知道"我是谁、用户是谁、我应该怎么回答"。这些信息不能凭空产生，得有初始模板。`workspace-init/` 就是这个模板——新用户来了，复制一份到他自己的工作区。

新用户首次使用时，这些文件会被复制到 `data/workspace/`：

| 文件 | 作用 | 示例内容 |
|------|------|---------|
| `soul.md` | Agent 人格定义 | "你是小趴，一个友善的工作助手..." |
| `user.md` | 用户画像 | "用户是 Python 初学者..." |
| `agent.md` | Agent 行为准则 | "回答要简洁，先给结论再解释" |
| `memory.md` | 长期记忆 | 用户和 Agent 交互中积累的记忆 |

> 💡 **实际场景**：你想让 XiaoPaw 在群里表现得专业一点——改 `agent.md`，让它"先讲结论再讲过程"。改完重启，下次对话就用新风格。这就是"人格定制"。

## 四、核心数据流详解

### 4.1 消息处理完整流程

> 📖 **概念小课堂：为什么看"数据流"很重要？**
>
> 看一个项目不是先看代码，而是先看"数据怎么走"。搞懂数据流，等于搞懂了项目的骨架——后面写代码就是往这个骨架上填肉。

```text
1. 用户在飞书发消息 "帮我搜索 Python 3.13 新特性"
   │
   │  接入层：消息进系统
   ▼
2. FeishuListener 收到消息（WebSocket 事件）
   - 防重放检查（ReplayCache）：这条消息处理过吗？处理过就忽略
   - 限流检查（RateLimiter）：这用户发太快了吗？太快就拒
   - 构造 InboundMessage(routing_key, content, sender_id, ...)
     ↑ 把飞书的原始消息包装成项目内部统一格式
   │
   │  调度层：排队分发
   ▼
3. Runner.dispatch(inbound) 把消息放入队列
   - 按 routing_key 分队列（同一用户串行处理）
     ↑ 比如用户 ou_xxx 的消息都进同一个队列，按顺序处理
   - 启动 Worker 协程（每个队列一个 Worker）
   │
   │  业务层：开始处理
   ▼
4. Runner._handle(inbound) 处理消息
   - 斜杠命令拦截（/new /help /status）：是命令就执行，不走 Agent
   - 获取/创建会话：找到这个用户的历史对话
   - 创建 CrewObservabilityAdapter：把 CrewAI 事件翻译成 Hook 事件
   - Hook: BEFORE_TURN（触发日志 + Langfuse 创建 trace）
     ↑ 开始一轮对话前，先打日志、建追踪
   - Hook: BEFORE_TOOL_CALL（pre-flight 安全检查）
     ↑ 调工具前，先检查安全（输入消毒）
   │
   │  业务层：AI 思考
   ▼
5. MainCrew 执行
   - before_llm_hook：注入历史 + 记忆 + 压缩上下文
     ↑ 把用户的记忆塞进 LLM 的提示词，让它知道上下文
   - Hook: BEFORE_LLM（记录 LLM 调用）
   - LLM 推理：理解意图 → 决定调用 skill_loader
     ↑ LLM 想："这是搜索需求，调 skill_loader 加载搜索技能"
   - Hook: BEFORE_TOOL_CALL（安全检查 skill_loader 调用）
   │
   │  执行层：在沙箱里跑代码
   ▼
6. SkillLoaderTool._run() 执行
   - 读取 SKILL.md 获取技能指令
     ↑ 从 skills/baidu_search/SKILL.md 读出技能说明
   - copy_context() 复制 ContextVar
     ↑ 把当前上下文复制一份，给子线程用
   - 在子线程构建 Sub-Crew
     ↑ Sub-Crew 是个独立的 Crew，专门跑这一个技能
   │
   │  执行层：真正跑代码
   ▼
7. SubCrew 在沙箱执行
   - 通过 MCP 协议调用 AIO-Sandbox
     ↑ 通过 HTTP 调用容器的 MCP 端点
   - 沙箱执行搜索代码
     ↑ 容器里跑 Python，调百度搜索
   - 每步触发 step_callback（Hook: AFTER_TURN）
     ↑ 每一步都打日志，方便追踪
   │
   │  执行层 → 业务层：结果回流
   ▼
8. 返回结果给 MainCrew
   - Hook: AFTER_TOOL_CALL（记录工具结果）
   - LLM 整理搜索结果
     ↑ LLM 把网页内容整理成人类可读的回答
   - Hook: AFTER_TURN（算账 + 循环检测）
     ↑ 统计这轮用了多少 token、有没有重复循环
   │
   │  调度层 → 接入层：发回用户
   ▼
9. Runner 发送回复
   - sender.send(routing_key, reply)
     ↑ 通过飞书 API 把回复发出去
   - 保存会话历史
     ↑ 把这轮对话存进 Session，下次能用
   - Hook: SESSION_END（审计 + flush Langfuse）
     ↑ 一轮结束，写审计日志、把追踪数据上传 Langfuse
```

> 💡 **实际场景**：以上流程完整跑一遍，大约 5-15 秒（取决于 LLM 响应速度和沙箱启动）。慢的部分是 LLM 推理（占 80% 时间）。所以优化 LLM 调用是性能关键。

### 4.2 关键数据结构

> 📖 **概念小课堂：什么是 `@dataclass`？**
>
> Python 写类要写一堆 `__init__`、`__repr__`，啰嗦。`@dataclass` 是个装饰器，加上它 Python 自动帮你生成这些样板代码——少写代码，少出 bug。

```python
# InboundMessage — 入站消息（飞书/TestAPI 都转换成这个格式）
@dataclass
class InboundMessage:
    """入站消息的统一格式

    不管消息来自飞书、TestAPI 还是 Cron，都包装成这个类
    这样下游模块不用关心消息来源，统一处理
    """
    routing_key: str        # 路由键（p2p:ou_xxx 或 group:chat_xxx）
    # ↑ 决定消息进哪个队列
    # ↑ p2p: 单聊；group: 群聊
    content: str            # 消息内容
    sender_id: str          # 发送者 ID
    msg_id: str             # 飞书消息 ID（防重放）
    # ↑ 同一条消息被推送两次时，用 msg_id 去重
    trace_id: str           # 链路追踪 ID
    # ↑ 贯穿整条调用链，方便日志追踪
    ts: str                 # 时间戳
    # ↑ 记录消息接收时间，用于审计

# MessageEntry — 会话历史条目
@dataclass
class MessageEntry:
    """会话历史的一条记录

    一个 Session 里有多条 MessageEntry，按时间顺序排列
    """
    role: str               # "user" 或 "assistant"
    # ↑ 区分是用户说的还是 AI 说的
    content: str            # 消息内容
    ts: str                 # 时间戳

# SenderProtocol — 发送器接口（抽象）
class SenderProtocol(Protocol):
    """发送器接口

    定义了"发送器"必须实现的方法
    FeishuSender 和 CaptureSender 都实现这个接口
    这样 Runner 不用关心具体用哪种发送器
    """
    async def send(self, routing_key: str, text: str) -> str: ...
    # ↑ 发送消息，返回消息 ID
    async def send_text(self, routing_key: str, text: str) -> None: ...
    # ↑ 发送纯文本消息
    async def send_thinking(self, routing_key: str) -> str | None: ...
    # ↑ 发送"思考中"状态，返回消息 ID（用于后续更新）
    async def update_card(self, card_id: str, text: str) -> None: ...
    # ↑ 更新已发送的卡片消息内容
```

**函数详解：InboundMessage 的构造**

```python

    routing_key="p2p:ou_abc123",
    content="帮我搜 Python 3.13",
    sender_id="ou_abc123",
    msg_id="om_def456",
    trace_id="trace_xyz789",
    ts="2026-07-10T10:00:00Z"
)
# ↑ 构造一个入站消息对象
# 之后传给 Runner.dispatch(msg) 即可

# 注意：
# - routing_key 必须以 "p2p:" 或 "group:" 开头
```

## 五、模块间依赖关系

> 📖 **概念小课堂：什么是"依赖关系"？**
>
> A 模块用了 B 模块的东西（import 了 B），就说 A 依赖 B。依赖关系不能乱——比如 A 依赖 B，B 又依赖 A，这就"循环依赖"了，类似死锁，Python 会报错。

```text
main.py
  ├── config/validator.py        (加载配置)
  ├── observability/logging_config.py  (初始化日志)
  ├── session/manager.py          (会话管理)
  ├── agents/main_crew.py        (构建 Agent)
  │     ├── memory/bootstrap.py   (注入记忆)
  │     ├── memory/context_mgmt.py (上下文管理)
  │     ├── tools/skill_loader.py  (技能加载)
  │     │     └── agents/skill_crew.py (构建 Sub-Crew)
  │     └── llm/aliyun_llm.py     (LLM 接入)
  ├── hook_framework/loader.py    (加载 Hook 策略)
  │     └── shared_hooks/*.py     (9 个策略实现)
  ├── runner.py                   (消息调度)
  ├── feishu/listener.py          (飞书监听)
  └── api/test_server.py         (TestAPI)
```

**为什么这样依赖？**

1. `main.py` 是入口，依赖所有需要装配的模块——它是"组装车间"，负责把所有零件拼起来。
2. `agents/main_crew.py` 依赖 `memory`、`tools`、`llm`——Agent 思考需要记忆、工具、LLM 三个助手。
3. `tools/skill_loader.py` 依赖 `agents/skill_crew.py`——加载技能时要构建 Sub-Crew 来执行。
4. `hook_framework/loader.py` 依赖 `shared_hooks/*.py`——Hook 框架本身不知道具体策略，只是加载它们。

### 依赖注入模式

> 📖 **概念小课堂：什么是"依赖注入"？**
>
> 想象买电脑——A 方案：CPU 焊死在主板上（紧耦合），换 CPU 要换主板；B 方案：CPU 插在插槽里（松耦合），换 CPU 直接拔插。依赖注入就是 B 方案——对象不在内部创建依赖，而是从外部传入。

项目大量使用"依赖注入"——对象不在内部创建依赖，而是从外部传入：

```python
# ❌ 不好的设计：内部创建依赖（紧耦合）
class Runner:
    def __init__(self):
        self.sender = FeishuSender()      # 写死了 FeishuSender
        # ↑ 想换成 CaptureSender 测试？改代码、重编译
        self.session_mgr = SessionManager()

# ✅ 好的设计：外部注入依赖（松耦合）
class Runner:
    def __init__(self, sender: SenderProtocol, session_mgr: SessionManager):
        # ↑ 构造函数接收两个参数
        self._sender = sender             # 可以是 FeishuSender 或 CaptureSender
        # ↑ 只要实现了 SenderProtocol 接口，谁都能传进来
        self._session_mgr = session_mgr
```

```text 逐行解释
__init__(self, sender: SenderProtocol, ...)
    self              → 实例自身
    sender            → 参数名
    : SenderProtocol  → 类型注解，告诉 IDE 和开发者"sender 应该实现这个接口"
    session_mgr       → 第二个参数
self._sender = sender
    self._sender      → 实例属性，前缀 _ 表示"内部使用"（约定）
    = sender          → 把传入的参数赋给属性
```

**函数详解：Runner 的依赖注入**

```python
class Runner:
    def __init__(
        self,
        sender: SenderProtocol,      # 发送器（必需）
        session_mgr: SessionManager, # 会话管理器（必需）
        config: AppConfig,           # 配置（必需）
        enable_test_api: bool = False # 是否开 TestAPI（可选）
    ):
        """
        Runner 的构造函数

        参数:
            sender: 实现了 SenderProtocol 的对象
                    生产用 FeishuSender，开发用 CaptureSender
            session_mgr: SessionManager 实例
            config: AppConfig 配置对象
            enable_test_api: 是否启动 TestAPI 调试接口

        返回值: 无（构造函数不返回）

        用法:
            runner = Runner(
                sender=FeishuSender(app_id, app_secret),
                session_mgr=SessionManager(),
                config=config,
                enable_test_api=True
            )
            await runner.start()

        注意:
            - sender 必须实现 send/send_text/send_thinking/update_card 四个方法
            - 测试时可以传 MockSender 不真正发消息
        """
        self._sender = sender
        self._session_mgr = session_mgr
        self._config = config
        self._enable_test_api = enable_test_api
```

## 六、设计模式总结

> 📖 **概念小课堂：什么是"设计模式"？**
>
> 设计模式是"前人踩坑总结的最佳实践"——遇到什么问题用什么模式，有套路。就像做菜的菜谱——红烧肉就那么几步，不用每次重新发明。XiaoPaw 用了 7 个常见模式。

| 模式 | 应用场景 | 代码位置 | 现实生活类比 |
|------|---------|---------|------------|
| 观察者模式 | Hook 事件分发 | `hook_framework/registry.py` | 订报纸：你订阅后，报社出新一期就送来 |
| 策略模式 | 9 个安全/可靠性策略 | `shared_hooks/*.py` | 支付方式：选微信、支付宝还是银行卡，各算各的 |

**重点模式详解：观察者模式（Hook 框架）**

```python
# 观察者模式的简化实现
class HookRegistry:
    """Hook 事件注册中心（观察者模式）

    功能：登记谁关心什么事件，事件发生时通知他们

    类比：报社订阅系统
        - subscribers 是订阅者名单
        - dispatch 是发新一期报纸
    """
    def __init__(self):
        self._subscribers = {}  # {事件名: [回调函数列表]}

    def subscribe(self, event: str, handler: callable):
        """订阅事件

        参数:
            event: 事件名（如 "BEFORE_TURN"）
            handler: 回调函数，事件发生时被调用

        用法:
            registry.subscribe("BEFORE_TURN", my_logger)
            # ↑ 注册 my_logger 监听 BEFORE_TURN 事件
        """
        if event not in self._subscribers:
            self._subscribers[event] = []
        self._subscribers[event].append(handler)

    async def dispatch(self, event: str, payload: dict):
        """触发事件

        参数:
            event: 事件名
            payload: 事件数据

        注意:
            - dispatch（普通分发）：异常被吞，不影响业务
            - dispatch_gate（门控分发）：异常会阻断业务
        """
        for handler in self._subscribers.get(event, []):
            # ↑ 遍历所有订阅了这个事件的回调
            try:
                await handler(payload)  # 依次调用
            except Exception as e:
                logger.error(f"Hook {event} failed: {e}")
                # ↑ 观测层 Hook 异常被吞，业务继续跑
```

> 💡 **实际场景**：用户发消息 → MainCrew 启动前，HookRegistry.dispatch("BEFORE_TURN") 被调用 → structured_log 记录日志、langfuse_trace 创建 trace。两个订阅者各自处理，互不影响。

**重点模式详解：工厂模式（构建 Crew）**

```python
# 工厂模式的简化实现：根据配置生产不同的 Crew
def build_agent_fn(config: AppConfig, memory: MemoryManager):
    """构建 Main Crew 的工厂函数

    参数:
        config: AppConfig 配置对象
        memory: 记忆管理器（注入历史和记忆）

    返回值:
        Crew 实例（已配置好 Agent + Task + 工具）

    用法:
        crew = build_agent_fn(config, memory)
        result = await crew.kickoff_async(inputs={"user_msg": "你好"})

    注意:
        - 每次调用都返回新实例（Crew 不能复用）
        - memory 是闭包捕获的，外部更新 memory 后这里也能看到
    """
    agent = Agent(
        role="Main Assistant",          # Agent 角色名

    )
    task = Task(
        description="处理用户消息: {user_msg}",
        expected_output="给用户的回复",
        agent=agent
    )
    return Crew(agents=[agent], tasks=[task],
                step_callback=make_step_callback())  # 注入回调
```

```text 逐行解释
def build_agent_fn(config, memory)
    工厂函数：输入原料（配置+记忆），输出成品（Crew 实例）
    类比：汽车厂进料（钢板+发动机），出车（整车）
Agent(role=..., goal=..., backstory=...)
    创建一个 Agent，相当于"招聘一个员工"
    backstory 来自 memory.get_soul()——从记忆里读人格设定
Crew(agents=[agent], tasks=[task], step_callback=...)
    把员工和任务组装成"项目组"
    step_callback 注入 Hook 适配器，让每步都触发 Hook
```

**重点模式详解：适配器模式（CrewAI 回调 → Hook 事件）**

```python
# 适配器模式：让 CrewAI 的回调"听起来像"XiaoPaw 的 Hook 事件
class CrewObservabilityAdapter:
    """把 CrewAI 的回调翻译成 Hook 事件

    CrewAI 内部有自己的事件（step_callback、task_callback）
    XiaoPaw 有自己的 Hook 事件（BEFORE_TURN、AFTER_TURN 等）
    两者格式不同，需要适配器转换

    类比：美标插头 → 国标插头的转接头
    """
    def __init__(self, hook_registry: HookRegistry, trace_id: str):
        self._hooks = hook_registry  # 保存 Hook 注册中心引用
        self._trace_id = trace_id    # 当前会话的追踪 ID

    def on_step(self, output):
        """CrewAI 的 step_callback 调用这个方法

        参数:
            output: CrewAI 的步骤输出对象
        """
        # 翻译成 XiaoPaw 的 AFTER_TURN 事件
        self._hooks.dispatch("AFTER_TURN", {
            "trace_id": self._trace_id,
            "step_output": str(output)
        })

    def on_task(self, task_output):
        """CrewAI 的 task_callback 调用这个方法"""
        self._hooks.dispatch("AFTER_TOOL_CALL", {
            "trace_id": self._trace_id,
            "result": task_output.result
        })
```

> 💡 **实际场景**：CrewAI 不知道 XiaoPaw 有什么 Hook，XiaoPaw 也不懂 CrewAI 的回调格式。适配器站中间翻译——CrewAI 该怎么跑还怎么跑，XiaoPaw 的 Hook 该触发就触发。

### 模式 1：异步上下文管理器（资源安全）


### 模式 2：ContextVar 传递上下文（避免参数穿透）

```python
# 项目里跨函数传递 trace_id 的标准写法
from contextvars import ContextVar

# 全局上下文变量（每个协程独立）
current_trace_id: ContextVar[str] = ContextVar("trace_id", default="")

async def handle_message(msg: InboundMessage):
    """处理消息时设置 trace_id，下层函数能读到"""
    token = current_trace_id.set(msg.trace_id)
    # ↑ 设置当前协程的 trace_id
    try:
        await do_something()  # 下层函数能通过 current_trace_id.get() 读到
    finally:
        current_trace_id.reset(token)
        # ↑ 恢复之前的值（防止污染外层）

async def do_something():
    # 不用参数传 trace_id，直接从 ContextVar 读
    tid = current_trace_id.get()
    logger.info(f"[{tid}] doing something")
```

```text 逐行解释
ContextVar("trace_id", default="")
    创建一个上下文变量，名字 "trace_id"，默认值空字符串
    每个协程看到的值独立（不会串台）
current_trace_id.set(msg.trace_id)
    设置当前协程的 trace_id
    返回 token 用于后续 reset
current_trace_id.reset(token)
    恢复 set 之前的值
    放在 finally 里保证异常时也能恢复
好处：避免把 trace_id 当参数层层传递（参数穿透）
```

### 模式 3：装饰器实现重试（可靠性）

```python
# 项目里防网络抖动的标准写法（utils/retry.py）
import asyncio
from functools import wraps

def async_retry(max_retries: int = 3, delay: float = 1.0):
    """异步重试装饰器

    参数:
        max_retries: 最大重试次数（默认 3）
        delay: 每次重试间隔秒数（默认 1.0）

    用法:
        @async_retry(max_retries=3, delay=0.5)
        async def call_llm(prompt):
            return await openai.chat.completions.create(...)

    注意:
        - 只捕获网络类异常（TimeoutError、ConnectionError）
        - 业务异常（如参数错误）不会重试
    """
    def decorator(func):
        @wraps(func)
        async def wrapper(*args, **kwargs):
            last_exc = None
            for attempt in range(max_retries):
                # ↑ 尝试 max_retries 次
                try:
                    return await func(*args, **kwargs)
                except (TimeoutError, ConnectionError) as e:
                    last_exc = e
                    logger.warning(f"Attempt {attempt+1} failed: {e}")
                    await asyncio.sleep(delay)
                    # ↑ 等一会儿再重试，避免狂打
            raise last_exc  # 重试完了还失败，抛出最后的异常
        return wrapper
    return decorator
```

## 七、典型调用链：从启动到处理消息

> 📖 **概念小课堂：什么是"启动流程"？**
>
> 项目不是上来就能跑的，要先"装配"——把配置加载好、组件创建好、连接关系建立好。就像开店营业前要先把员工就位、设备通电、货架摆满。

```python
# main.py 的简化版启动流程（实际代码更复杂，这里突出关键步骤）
async def main():
    # === 阶段 1：加载配置 ===
    raw_config = yaml.safe_load(open("config.yaml"))
    config = AppConfig(**raw_config)
    # ↑ Pydantic 校验配置，错误立即退出

    # === 阶段 2：初始化日志 ===
    setup_logging(config.observability)
    logger = logging.getLogger("xiaopaw")
    logger.info("XiaoPaw starting...")

    # === 阶段 3：创建组件（依赖注入）===
    session_mgr = SessionManager(config.session)
    memory_mgr = MemoryManager(config.memory)
    hook_registry = HookRegistry()
    # ↑ 创建各个组件，配置都通过构造函数注入

    # === 阶段 4：加载 Hook 策略 ===
    hook_loader = HookLoader(hook_registry)
    hook_loader.load("shared_hooks/hooks.yaml")
    # ↑ 从 YAML 加载 9 个策略，注册到 hook_registry

    # === 阶段 5：构建 Agent 工厂 ===
    agent_fn = build_agent_fn(config, memory_mgr, hook_registry)

    # === 阶段 6：创建 Runner（核心调度器）===
    if config.debug.enable_test_api:
        sender = CaptureSender()  # 开发模式：打印到终端
    else:
        sender = FeishuSender(config.feishu)  # 生产模式：真发飞书

    runner = Runner(
        sender=sender,             # 注入发送器
        session_mgr=session_mgr,  # 注入会话管理
        agent_fn=agent_fn,        # 注入 Agent 工厂
        config=config
    )

    # === 阶段 7：启动服务 ===
    if config.debug.enable_test_api:
        await start_test_api(runner, config.debug)  # 启 TestAPI
    await runner.start()  # 启动消息队列

    # === 阶段 8：启动飞书监听 ===
    listener = FeishuListener(config.feishu, runner)
    await listener.start()  # 阻塞在这里，持续监听消息
```

```text 逐行解释
阶段 1：加载配置
    读 config.yaml，用 Pydantic 校验
    错误立即退出（启动失败比运行时崩溃好）
阶段 2：初始化日志
    配置日志格式、输出位置
    后续所有模块都用这个 logger
阶段 3：创建组件
    每个组件都通过构造函数接收配置
    组件之间不互相创建，都由 main.py 装配
阶段 4：加载 Hook 策略
    从 YAML 声明式加载，不写死在代码里
    改策略只改 YAML，不用改代码重编译
阶段 5：构建 Agent 工厂
    返回一个函数，调用时返回新的 Crew
    Crew 不能复用（每次对话要新实例）
阶段 6：创建 Runner
    根据是否开发模式选择不同 sender
    这就是依赖注入的好处：换实现不改代码
阶段 7-8：启动服务
    TestAPI 是开发调试入口
    FeishuListener 是生产入口
    两个入口最终都调 Runner.dispatch
```

> 💡 **实际场景**：启动失败时看日志。Pydantic 校验失败的报错很清晰——会告诉你哪个字段、什么问题、期望什么类型。比如 `test_api_port: field must be int` 说明配置里写成了字符串。

## ❓ 常见问题

**Q1：为什么 `xiaopaw/` 和 `shared_hooks/` 要分开放？**

A：因为业务代码（xiaopaw）会频繁改，加固层（shared_hooks）相对稳定。分开后，改业务不会动到加固策略，改加固策略也不影响业务。这就是"关注点分离"——一个目录管一件事。

**Q2：`workspace-init/` 里的 `.md` 文件为什么用 Markdown？**

A：因为这些文件的内容是给 AI 看的"提示词"。Markdown 格式结构清晰（标题、列表、段落），AI 容易理解。比纯文本好，比 JSON 灵活。

**Q3：13 个技能是怎么被自动发现的？**

A：`load_skills.yaml` 文件里列出启用的技能名。SkillLoaderTool 启动时读这个文件，知道有哪些技能可用。每个技能目录里有 `SKILL.md` 描述技能——用户问问题时，MainCrew 根据描述选合适的技能。

**Q4：Session 是怎么存的？内存还是文件？**

A：默认内存（快但重启丢失）。生产环境建议改文件或数据库存储——看 `session/manager.py` 的实现。Session 存对话历史，丢了用户得重新说一遍上下文。

**Q5：为什么 Sub-Crew 要在子线程跑？**

A：CrewAI 的 Crew 执行是同步阻塞的，但 Runner 是 asyncio 异步的。在异步环境里跑同步代码会卡住事件循环。所以用 `run_in_executor` 把 Sub-Crew 丢到子线程跑，主线程继续处理其他消息。

**Q6：Hook 框架是怎么挂载到 CrewAI 的？**

A：CrewAI 提供了 `step_callback` 和 `task_callback` 两个回调点。`CrewObservabilityAdapter` 实现这两个回调，把 CrewAI 的内部事件翻译成 XiaoPaw 的 7 个 Hook 事件（5 个标准 + 2 个扩展）。详见 `hook_framework/crew_adapter.py`。

**Q7：模块之间是怎么避免循环依赖的？**

A：通过"依赖倒置"——高层不依赖低层，都依赖抽象接口。比如 Runner 依赖 `SenderProtocol` 接口，不依赖具体的 `FeishuSender`。这样 FeishuSender 可以反过来用 Runner 的功能（如果需要），不会循环。
