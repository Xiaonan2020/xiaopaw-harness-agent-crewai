## 一、XiaoPaw 是什么？

> 📖 **概念小课堂：什么是"AI 助手"？**
>
> 想象一下你公司里有这么一个同事：你随时可以发消息给他，说"帮我查一下 Python 3.13 有什么新特性"，他就去搜、整理、回复你。AI 助手就是这位"同事"的数字版——它由 AI 模型驱动，能理解你的话、调用工具、给你答案。
>
> XiaoPaw（小趴）就是这样一个角色，只不过它住在飞书（Lark）这个工作软件里。

**XiaoPaw（小趴）是一个运行在飞书（Lark）里的 AI 工作助手**。你在飞书里发消息给它，它会理解你的意图、调用合适的技能、在隔离的沙箱里执行代码，最后把结果返回给你。

### 核心能力

下面这张图展示了 XiaoPaw 收到一条消息后，内部经历的完整流程。每个箭头代表"下一步要做的事"。

```text
用户在飞书发消息："帮我搜索一下 Python 3.13 有什么新特性"
                          │
                          │  飞书把消息通过 WebSocket 推送给 XiaoPaw
                          ▼
┌─────────────────────────────────────────────────────────┐
│  XiaoPaw 收到消息                                        │
│  1. 理解意图 → 需要搜索                                   │  ← AI 在这里"读懂"你的话
│  2. 选择技能 → baidu_search                              │  ← 从技能清单里挑一个
│  3. 在沙箱中执行搜索代码                                   │  ← 在隔离环境跑代码
```

## 二、整体架构一览

### 数据流：一条消息从接收到回复

> 📖 **概念小课堂：什么是"架构图"？**
>
> 架构图就像一栋楼的"楼层平面图"——它告诉你每个房间（模块）做什么、谁和谁相连（数据怎么流）。看不懂架构图没关系，我们逐个方框讲。

**逐层解读：**

| 层级 | 模块 | 做什么 | 为什么需要它 |
|------|------|--------|------------|
| 接入层 | FeishuListener | 监听飞书消息 | 把外部消息"翻译"成项目内部格式 |

### 两层 Agent 架构

> 📖 **概念小课堂：什么是"Agent"？**
>
> Agent（智能体）= 一个会"思考-行动-观察"循环的 AI 程序。它不像传统代码那样按固定流程跑，而是自己判断下一步该干什么。你可以理解为：**传统程序是"自动售货机"，Agent 是"会自己挑货的售货员"**。

这是项目最核心的设计：

| 层级 | 名称 | 职责 | 运行环境 |
|------|------|------|---------|
| 第一层 | Main Crew | 理解用户意图、选择技能、维护对话上下文 | 主进程 |
| 第二层 | Sub-Crew | 在沙箱里执行单一技能（搜索、文档处理等） | Docker 容器 |

**为什么要分两层？**

想象一个公司：老板（Main Crew）只负责接电话、分配任务；工人（Sub-Crew）在车间里干活。如果工人在车间出了事故，老板安然无恙——这就是"隔离"。具体到代码层面：

1. **控制上下文长度**：Main Crew 的 prompt（提示词）里只有技能名称和描述（一两行），不会被庞大的工具 schema（参数定义）撑爆
2. **安全隔离**：Sub-Crew 在 Docker 沙箱里执行代码，即使出问题也不影响主进程
3. **渐进式披露**：LLM 只看到"技能清单"，需要时才加载具体实现

> 💡 **实际场景**：用户说"帮我搜 Python 3.13 新特性"。
> - Main Crew 想："哦，这是搜索需求，应该用 baidu_search 技能。"
> - Sub-Crew 在沙箱里跑："好的，我去百度搜，把结果整理好。"
> - 沙箱万一崩了：Main Crew 不受影响，可以重试或换技能。

## 四、关键概念解释

### 1. Agent（智能体）

> 📖 **概念小课堂：Agent vs 普通程序**
>
> - 普通程序：你写 `if 用户说"搜索" then 调用搜索函数`——它是死的。
> - Agent：你给 AI 一个目标（"帮用户解决问题"），它自己决定下一步该搜索还是该写文档——它是活的。

Agent 是一个能"思考-行动-观察"循环的 AI 程序。它不像传统程序那样按固定流程执行，而是：

```text
思考(Thought) → 行动(Action) → 观察(Observation) → 再思考...
```

在 XiaoPaw 里，CrewAI 框架帮我们实现了这个循环。

**函数详解：Agent 的核心循环**

```python
# CrewAI 内部的核心循环（简化版，便于理解）
def agent_loop(task, max_iter=50):
    """
    Agent 的"思考-行动-观察"循环

    参数:
        task: Task 对象，包含目标描述
        max_iter: int，最大循环次数（防止 AI 无限思考）

    返回值:
        str: 最终答案
    """
    for i in range(max_iter):  # 最多循环 50 次，防止烧钱
        # 1. 思考：让 LLM 决定下一步该做什么
        thought = llm.chat(task, history)
        if thought.is_final_answer:  # 如果 LLM 觉得已经有答案了
            return thought.text  # 返回最终结果
        # 2. 行动：调用 LLM 选中的工具
        observation = tool.run(thought.action)
        # 3. 把观察结果塞回历史，进入下一轮
        history.append(observation)
    return "达到最大迭代次数，强制停止"
```

> 注意：`max_iter=50` 是防止 AI 陷入"思考死循环"——LLM 有时会反复纠结同一个问题，必须设上限避免烧钱。

### 2. Crew（编排）

> 📖 **概念小课堂：Crew = 项目组**
>
> 想象一个项目组：有项目经理、有执行者、有具体任务清单。CrewAI 把这个组织形式抽象成了代码——一个 Crew 就是"一组 Agent + 一组 Task + 协作规则"。

Crew 是一组 Agent 协作完成任务的编排单位。可以理解为一个"项目组"：

- **Main Crew**：像一个项目经理，理解需求、分配任务
- **Sub-Crew**：像一个专业执行者，在沙箱里完成具体技能

### 3. MCP（Model Context Protocol）

> 📖 **概念小课堂：MCP 是 AI 世界的"USB 接口"**
>
> 电脑有 USB 接口，插什么设备都能用——鼠标、键盘、U 盘。MCP 就是 AI 的 USB：AI 想调外部工具（搜网页、读文件、跑代码），都走同一个协议，不用每个工具单独写对接代码。

MCP 是一个标准协议，让 AI 能调用外部工具。类似于 REST API，但专为 AI 设计：

```text
AI 发出请求 → MCP Server 接收 → 在沙箱里执行 → 返回结果给 AI
```

AIO-Sandbox 就是一个 MCP Server，它运行在 Docker 容器里，提供文件读写、代码执行等能力。

**函数详解：MCP 调用流程（简化）**

```python
# MCP 调用的简化伪代码，展示真实项目里怎么用
async def call_mcp_tool(tool_name: str, args: dict, timeout: int = 120):
    """
    通过 MCP 协议调用沙箱里的工具

    参数:
        tool_name: str，工具名（如 "run_python"）
        args: dict，工具参数（如 {"code": "print('hi')"}）
        timeout: int，超时秒数（默认 120 秒）

    返回值:
        dict，工具执行结果

    用法:
        result = await call_mcp_tool("run_python", {"code": "print(1+1)"})
        print(result["text"])  # 输出: 2

    注意:
        - 如果沙箱卡死，会超时抛 asyncio.TimeoutError
        - 沙箱崩了会返回 connection refused
    """
    payload = {"jsonrpc": "2.0", "method": "tools/call",
               "params": {"name": tool_name, "arguments": args}}
    # ↑ 构造 MCP 请求体（JSON-RPC 2.0 格式）
    async with aiohttp.ClientSession() as session:
        async with session.post(SANDBOX_URL, json=payload,
                               timeout=timeout) as resp:
            return await resp.json()  # 等待沙箱返回结果
```

### 4. Hook（钩子）

> 📖 **概念小课堂：Hook 像海关检查点**
>
> 你出海关时，行李要过 X 光、人要查验护照。这些"检查点"就是 Hook——在固定位置强制执行检查，谁也绕不过。XiaoPaw 里有一句话：**"Prompt is advice, Hook is law"**（提示词是建议，Hook 是法律）——AI 可能不听 prompt，但 Hook 一定会执行。

Hook 是在特定事件发生时自动执行的回调函数。类似数据库的触发器：

```text
事件发生 → Hook 框架分发 → 多个 Handler 依次执行
```

XiaoPaw 定义了 5+2 个事件点，在每个关键节点插入安全检查和观测逻辑。

> 💡 **实际场景**：用户让 AI 写一个删文件的脚本。如果没有 Hook，AI 可能真的执行了——数据丢失。有了 `sandbox_guard.py` Hook，在"调用工具前"这一事件点检查：发现代码里有 `rm -rf`，直接拒绝执行，保护系统。

### 5. 沙箱（Sandbox）

> 📖 **概念小课堂：沙箱 = 隔离病房**
>
> 想象医院里的隔离病房：里面病人接触过的东西不会污染外部，因为房间是密封的。沙箱就是这个隔离病房——AI 写的代码在里面跑，即使有病毒（恶意代码），也跑不出这个房间。

沙箱是一个隔离的执行环境。AI 生成的代码在这里运行，即使有恶意行为也无法影响宿主系统：

```text
Docker 容器（沙箱）
  ├── 文件系统隔离    ← 看不到宿主机的文件
  ├── 进程隔离        ← 杀不了宿主机的进程
  ├── 网络限制        ← 不能随便访问内网
  └── 权限控制        ← 没有管理员权限
```

## 六、技术选型的底层原理

### 为什么用 asyncio 而不是多线程？

```python
# 多线程模型（问题：GIL 限制 + 线程切换开销大）
# GIL = Python 全局解释器锁，同一时刻只有一个线程能跑 Python 代码
Thread 1: 等待飞书消息    # 阻塞，占着 GIL
Thread 2: 等待 LLM 响应   # 也想用 GIL，被堵
Thread 3: 等待沙箱返回    # 同上

# asyncio 模型（优势：单线程 + 事件循环 + 零切换开销）
# 单线程就够了，因为大部分时间都在"等"网络响应
单线程事件循环:
  ├── 消息到达 → 处理消息    # 谁准备好了就处理谁
  ├── LLM 响应到达 → 处理响应
  └── 沙箱返回 → 处理结果
```

XiaoPaw 是 IO 密集型应用（大量等待网络响应），asyncio 能用单线程处理高并发。

> 📖 **概念小课堂：GIL 是什么？**
>
> GIL（Global Interpreter Lock，全局解释器锁）是 Python 的一个设计妥协。它规定：同一时刻，只有一个线程能执行 Python 字节码。这意味着"多线程"在 Python 里其实不能真正并行——所以 IO 密集场景下，asyncio 反而更高效。

### 为什么用 CrewAI 而不是 LangChain Agent？

| 特性 | LangChain Agent | CrewAI |
|------|----------------|--------|
| 抽象层级 | 单个 Agent | Agent + Crew + Task |
| 多 Agent 协作 | 需手动编排 | 内置 Crew 编排 |
| 回调机制 | 有限 | step_callback / task_callback |
| 生产就绪 | 需大量封装 | 开箱即用 |

CrewAI 的 Crew 抽象天然支持"两层 Agent"架构，且回调机制方便接入 Hook 框架。

### 为什么用 Pydantic 做配置？

```python
# ❌ 没有 Pydantic 的问题
config = yaml.safe_load(open("config.yaml"))
port = config["debug"]["test_api_port"]  # 可能 KeyError：key 不存在就崩
# 如果 port = -1，运行时才发现错误（比如端口不能用）
# 错误信息难懂，调试困难

# ✅ 有 Pydantic 的优势
from pydantic import BaseModel, Field

class DebugConfig(BaseModel):
    # ↑ 定义一个配置类，继承 BaseModel
    test_api_port: int = Field(default=9090, ge=1024, le=65535)
    # ↑ 字段：类型 int；默认 9090；最小 1024，最大 65535
    # 启动时即校验：端口必须在 1024-65535 之间
```

```text 逐行解释
class DebugConfig(BaseModel):
    定义一个类，继承自 Pydantic 的 BaseModel，告诉 Pydantic "这是个配置模型"

test_api_port: int = Field(default=9090, ge=1024, le=65535)
    字段名: test_api_port
    类型: int（必须是整数）
    Field(...) 给字段加约束:
        default=9090    → 不填时默认 9090
        ge=1024         → 必须 ≥ 1024（大于等于）
        le=65535        → 必须 ≤ 65535（小于等于）
```

配置错误在启动时就暴露，而不是运行时崩溃。这就是"快速失败"原则——早死早超生，问题越早暴露修复成本越低。

## 七、项目的优势与局限性

### 优势

1. **零侵入加固**：9 个安全策略通过 YAML 声明接入，业务代码 0 行修改
2. **渐进式能力披露**：LLM 上下文始终保持小尺寸，响应稳定
3. **全链路可观测**：Langfuse 追踪从消息到回复的完整调用链
4. **安全隔离**：沙箱执行 + 输入消毒 + 权限网关三层防护

### 局限性

1. **依赖外部 LLM**：Qwen3-max 的响应质量和速度影响用户体验
2. **单机部署**：当前设计不支持水平扩展（Session 状态在内存中）
3. **沙箱启动开销**：每次技能调用都要等待 MCP 连接，约 1-2 秒延迟
4. **飞书平台绑定**：消息收发依赖飞书 SDK，迁移到其他平台需要改造

> 💡 **实际场景**：如果你想把 XiaoPaw 从飞书搬到钉钉，只需替换 `feishu/` 目录下的监听器和发送器，业务层（agents、skills、memory）完全不用动。这就是分层架构的好处。

## 七、项目四代演进详解

> 📖 **概念小课堂：为什么要"演进"而不是"一步到位"？**
>
> 想盖一栋楼——地基没打好就盖十层会塌。XiaoPaw 也是从简单到复杂一步步长大的。每一代都在前一代基础上加东西，不会推倒重来。这种"渐进式增强"是工程实践的核心思想。

### 第一代（L17）：能力骨架——先让它能"对话"

```text
用户消息 → [单一 Agent + 1 个工具] → 回复
```

第一代只做了最基本的事：能收消息、能回复。Agent 只有一个工具（比如搜索），prompt 里写死"用户说话就调这个工具"。

```python
# 第一代的简化代码
agent = Agent(
    role="助手",
    goal="回答用户问题",
    tools=[search_tool]  # 只有搜索一个工具
)
crew = Crew(agents=[agent], tasks=[task])
```

### 第二代（L22）：三层记忆——让它"记住你"

```text
用户消息 → [Agent + 记忆系统] → 回复
              ↑
        三层记忆：
        - Bootstrap（出厂记忆）
        - 文件记忆（memory.md）
        - 向量记忆（语义搜索）
```

第二代加了"记忆"——让 AI 记住你是谁、之前聊过什么。否则每次对话都像失忆患者，体验极差。

### 第三代（L29）：两层 Agent——让它"动手干活"

```text
用户消息 → [Main Crew（思考）] → [Sub-Crew（沙箱执行）] → 回复
```

第三代把单一 Agent 拆成两层：Main Crew 只思考不干活，Sub-Crew 在沙箱里跑代码。这是架构上的关键转折——安全和上下文管理都因此受益。

### 第四代（L30-33）：系统加固——让它"可靠不上头"

```text
用户消息 → [Main Crew + Hook 框架] → [Sub-Crew + 沙箱守卫] → 回复
              ↑                          ↑
            9 个策略                   输入消毒
            成本围栏                   权限网关
            循环检测                   审计日志
```

第四代加了 9 个安全/可靠性策略，通过 Hook 框架接入。这是从"能跑"到"能上生产"的关键——生产环境 AI 不能烧钱、不能泄露数据、不能卡死。

### 演进的核心规律

| 规律 | 含义 | 例子 |
|------|------|------|
| 先跑通再优化 | 第一版丑没关系，能跑就行 | 第一代代码很糙，但能对话 |
| 每代只加一个核心能力 | 不要一次加太多，否则难调试 | 第二代只加记忆，不动 Agent 架构 |
| 加固放在最后 | 业务逻辑稳定后再加固，避免反复改 | 第四代才加 Hook，因为前三代业务已稳定 |

> 💡 **实际场景**：你跟着教程学到 L17 时会觉得"代码好简单"——这是对的。不要急，按顺序学。每一代都建立在前一代基础上，跳着学会"看不懂为什么这么设计"。

## ❓ 常见问题

**Q1：XiaoPaw 和 ChatGPT、文心一言这些通用 AI 有什么区别？**

A：通用 AI（ChatGPT）只会在对话框里回答问题，不能"动手"。XiaoPaw 是企业级 Agent——它能调工具、跑代码、读写文件、操作飞书。简单说：通用 AI 是"嘴"，XiaoPaw 是"嘴 + 手"。

**Q2：我必须用飞书吗？能不能换成微信/钉钉？**

A：飞书是当前主接入点，但架构上做了抽象（`SenderProtocol` 接口）。换平台只需实现一个新的监听器和发送器，业务层不动。但本教程以飞书为主。

**Q3：Qwen3-max 是必须的吗？能用 GPT-4 吗？**

A：技术上可以——LLM 接入层做了抽象。但教程示例配置是 Qwen3-max，因为它中文好、成本低、国内合规。换 GPT-4 需要改 LLM 配置和接入代码。

**Q4：沙箱一定要用 Docker 吗？虚拟机行不行？**

A：Docker 启动快（秒级）、资源占用小。虚拟机太重（分钟级启动），不适合"每次技能调用都启容器"的场景。如果不能用 Docker，可以降级用 subprocess + seccomp 隔离，但安全性差很多。

**Q5：9 个 Hook 策略一定要全部启用吗？**

A：不一定。`hooks.yaml` 里可以单独开关每个策略。学习阶段可以全关，生产环境建议全开。但 `sandbox_guard` 和 `permission_gate` 这种安全策略，建议任何时候都开。

**Q6：我没有阿里云账号，能学这个项目吗？**

A：可以。LLM 部分可以换成 OpenAI、DeepSeek、智谱等任何兼容 OpenAI 协议的服务。沙箱部分只要能跑 Docker 就行。但飞书机器人需要飞书开发者账号（免费注册）。

## 🔧 调试技巧

**技巧 1：开 TestAPI 调试，不用每次开飞书**

在 `config.yaml` 里设 `debug.enable_test_api: true`，就能用 `curl http://localhost:9090/chat` 直接发消息测试。开发时不用打开飞书，效率高 10 倍。

**技巧 2：日志看不懂时，开 JSON 格式关闭**

`observability.log_json: true` 输出结构化日志（方便机器解析）。但人看的话，关掉它，输出更易读的文本日志。

**技巧 3：沙箱卡死了怎么办**

```bash
docker ps -a | grep sandbox     # 找到沙箱容器
docker restart <容器名>          # 重启它
```

如果反复卡死，多半是某个技能代码里有死循环——查 `data/workspace/` 下最近的日志。

**技巧 4：LLM 调用失败，先看 API Key**

最常见的错误是 `401 Unauthorized`——API Key 没设对。验证命令：

```bash
# Windows PowerShell
echo $env:QWEN_API_KEY

# macOS / Linux
echo $QWEN_API_KEY
```

输出应该是 `sk-xxx...` 格式。如果是空，说明环境变量没设。

**技巧 5：Hook 报错但不影响业务？**

这是设计——观测层 Hook（structured_log、langfuse_trace）的异常会被吞掉，不影响业务。但如果安全层 Hook（sandbox_guard）报错，业务会被阻断。看日志区分是哪一层。
